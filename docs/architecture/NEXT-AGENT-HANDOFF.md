7. Lead и Student funnel используют один редактор с параметром типа клиента, областью, версиями и публикацией.
8. В продукте должна остаться одна каноническая модель задач.
9. Аналитика читает операционные домены и не создаёт вторую бизнес-истину.
10. Исправляй корневую причину в общей точке, а не симптом на одном экране.

Утверждённое правило доступа к настройкам:
- Директор редактирует организационные и расписательные настройки школы.
- Управляющий по умолчанию только просматривает настройки назначенных ему филиалов.
- Директор может отдельно выдать или отозвать конкретному Управляющему делегированное право редактирования.
- Делегирование действует только в пределах уже назначенных Управляющему филиалов.
- Оно не даёт общешкольного редактирования и не может передаваться Управляющим дальше.
- Выдача, отзыв и изменения по делегированному праву аудируются.

Не начинай с повторного глобального аудита: он уже выполнен. В начале проверь только актуальность ветки, production routes и того вертикального сценария, который берёшь в работу. Если код противоречит карте, зафиксируй доказательство и обнови карту вместе с исправлением.

Правила выполнения каждого этапа:
1. Сначала проследи реальный flow end-to-end и всех callers общей функции.
2. Сними доизменительный API/data baseline.
3. Сделай минимальное корневое изменение в общей точке.
4. Переведи всех production consumers.
5. Добавь минимальные runnable checks, которые ловят регрессию.
6. Запусти analyze, targeted и full tests в пропорции к риску.
7. Проверь реальный Windows/Android сценарий.
8. Только после parity удали старый путь.
9. Обнови PRODUCT-ESSENCE-MAP.md, если обнаружен подтверждённый новый факт или изменено бизнес-решение.

Запрещено:

- дробить backend на микросервисы;
- добавлять новую дизайн-систему поверх v7;

- выполнять production deployment без финального подтверждения;
- уходить в глубокий security-аудит до завершения продуктового UX, кроме предотвращения явной регрессии доступа/данных.

Коммуникация:

Начни с этапа 0, затем возьми этап 1 как первый implementation slice. Не возвращайся к составлению ещё одного глобального списка: карта и приоритет уже зафиксированы.

## 4. Красные флаги в работе следующего агента

Работу нужно остановить и скорректировать, если агент:

- сразу объявляет старые задачи выполненными по тестам;
- начинает новый полный аудит без использования Product Essence Map;
- создаёт ещё один календарь, funnel editor, task model или Settings screen;
- исправляет только UUID клиента, не находя общий navigation root;
- предлагает переписать приложение или backend с нуля;
- меняет production API без трассировки всех callers;
- удаляет legacy-код до миграции данных;
- часами пишет отчёт без изменения или проверяемого результата;
- смешивает скидку с редактированием проведённой оплаты;
- считает security главным блокером вопреки текущему приоритету владельца;
- деплоит production без явной команды и rollback-плана.

## 5. Контрольные вопросы владельца после каждого этапа

Владелец может проверять прогресс пятью вопросами:

1. Что изменилось в реальном пользовательском сценарии?
2. Какая общая корневая причина устранена?
3. Какие старые пути после parity были удалены?
4. Чем результат проверен на реальном Windows/Android аккаунте?
5. Что осталось ENGINEERING PASS, но ещё не прошло OWNER UAT?

Если на первый вопрос нет демонстрируемого ответа, этап ещё не завершён.

## 6. Ожидаемый итог работы агента

Следующий агент должен передать владельцу:

- работающее приложение, а не только документы;
- список реализованных вертикальных сценариев;
- список удалённых параллельных путей;
- результаты analyze/tests/build;
- реальную роль/device/UAT-матрицу;
- Windows release и APK с версией и SHA-256;
- backend migration/deploy evidence, если сервер действительно менялся;
- честный список оставшихся ограничений без искусственного процента готовности.

Финальное слово «готово» допустимо только после демонстрации владельцу и его приёмки.
