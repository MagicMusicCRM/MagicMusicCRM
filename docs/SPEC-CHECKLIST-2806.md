## 5. Сквозное требование: поиск в длинных списках (✔ заказчик 16.07)

**Правило: любой выпадающий список, где вариантов может быть больше 10, заменяется на строку поиска.** После ввода текста показываются **5 наиболее подходящих** вариантов; во время ввода список обновляется аккуратно (без «прыжков», с debounce).

### ✔ Уточнение заказчика 16.07: «поиск по всем совпадающим данным, но реализовать правильно»

Искать нужно **по всем полям записи** (ФИО, телефон, email, и т.д.), а не только по видимой подписи.

**Такой поиск на бэкенде уже есть — и в нём ровно те дефекты, которые «реализовать правильно» и означает.** `buildStudentSearchFilter` (`crm.service.ts:851`):
```sql
lower(concat_ws(' ', p.first_name, p.last_name, u.email, p.phone, s.custom_data::text))
  like lower('%' || $1 || '%')
```
Что здесь не так:
- [ ] **Телефон не нормализуется.** В базе `+79161234567`, пользователь набирает `8916…` или `916…` → **не найдётся**. При этом канонизатор уже написан и используется в импорте/матчинге: `normalizePhoneRu` + SQL-близнец `normalizedPhoneExpr` (`phone.util.ts`). Нужно: если запрос похож на телефон — нормализовать и сравнивать с `normalizedPhoneExpr('p.phone')`
- [ ] **`custom_data::text` даёт ложные срабатывания** — в подстроку попадают **ключи JSON и UUID'ы**, а не только значения: запрос `level` найдёт всех, у кого есть такое поле; кусок UUID «найдёт» случайные записи. Нужно искать по значениям (`jsonb_each_text`), а не по сырому тексту JSON
- [ ] **Нет индекса → seq scan.** `like '%…%'` с ведущим `%` не берёт btree, а `pg_trgm`/GIN в проекте **не подключён ни разу** (проверено по всем миграциям). На 1.5к учеников терпимо, на росте — деградация. Нужно: расширение `pg_trgm` + GIN-индекс по поисковому выражению
