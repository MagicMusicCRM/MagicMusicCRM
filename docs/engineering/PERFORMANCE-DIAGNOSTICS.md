# Измерение клиент → API → PostgreSQL

## Сбор измерений

На сервере существующий HTTP middleware пишет одну структурированную запись
`event: http.performance` при завершении запроса или разрыве соединения. Она
содержит шаблон маршрута, статус, requestId, operationId и числовые измерения БД.
Ручное включение SQL-логирования не требуется. Проверки health не пишут эти записи.

Flutter хранит последние 200 записей в `AppPerformance.snapshot`, добавляет
измерения в breadcrumbs существующего Sentry и может печатать JSON-строки при
`--dart-define=PERFORMANCE_LOGS=true`. Отправка новых Sentry traces не включалась;
breadcrumbs не являются хранилищем всех успешных запросов. Для сравнения скорости
нужна профильная сборка на одном устройстве с одинаковым набором данных.

Пример запуска против уже запущенного локального API из корня репозитория:

```powershell
flutter run -d windows --profile --dart-define=PERFORMANCE_LOGS=true --dart-define=MAGIC_API_BASE_URL=http://127.0.0.1:3000/api | Tee-Object -FilePath outputs/performance-client.log
```

После выполнения сценариев и завершения записи:

```powershell
node server/scripts/summarize-performance.cjs outputs/performance-client.log
```

Тот же инструмент принимает файл stdout сервера и несколько файлов измерений.
Он считает число наблюдений, ошибки, медиану, p95 и максимум по каждому сценарию.
P95 — nearest-rank. Для отсутствующих Server-Timing указывается реальное число
наблюдений, а не подставляется ноль. Предел — 100000 измерений за запуск; для
большего объёма выбрать более короткий интервал. Сырые идентификаторы и исходные
строки в сводку не переносятся.

## Что измеряется

| Запись / поле | Значение |
| --- | --- |
| operation.durationMs | Полная длительность обёрнутого вызова, включая refresh сессии, паузы и повторы; для экранов — также ожидание следующего кадра |
| http.durationMs | Одна попытка HTTP через Dio, включая получение/преобразование ответа; неудачные попытки тоже учитываются |
| screenData / screenFrame | Время до завершения основной загрузки карточки/расписания и до следующего кадра видимого экрана |
| durationMs в http.performance / serverMs в Flutter | Серверное время до finish/close; Server-Timing снимается раньше, перед отправкой заголовков |
| dbQueryMs / dbAcquireMs | Сумма времени вызовов SQL / получения соединения из пула; dbMaxQueryMs — самый долгий вызов; dbMaxWaiting — максимум очереди перед получением соединения |

`dbAcquireMs` включает ожидание свободного соединения и установку нового, если
это потребовалось. `dbQueryMs` включает время драйвера, сетевой обмен с БД и
ожидание блокировок; это не чистое CPU-время SQL в PostgreSQL. Параллельные SQL
складываются, поэтому сумма может превышать длительность HTTP-запроса. Нельзя
получать «время бизнес-логики» вычитанием этих сумм из общего времени.

`screenFrame` означает следующий кадр после основной загрузки, а не полную
готовность всех ленивых панелей и не измерение GPU raster time. В расписании
дозагрузка выбранного дня остаётся отдельной фоновой работой. Оплата и команды
занятий измеряются до ответа API, включая автоматические повторы; закрытие
диалога и последующее обновление экранов не входят в эту длительность.
`completed` означает завершение Future, не подтверждение бизнес-успеха: экран
может обработать ошибку внутри загрузчика. Ошибки HTTP видны отдельными записями.

## Как найти причину задержки

Сопоставить клиентский `http.requestId` с серверным `requestId`; `operationId`
объединяет несколько запросов одной загрузки экрана. RequestId денежной команды
сохраняется при повторе вместе с Idempotency-Key. Для различения её HTTP-попыток
использовать отдельные записи и их порядок; один requestId может встречаться
несколько раз. Сервер также валидирует входные идентификаторы.

Большое dbAcquireMs указывает на получение соединения, большое dbQueryMs — на
вызовы БД; точную причину внутри SQL проверять планами/статистикой PostgreSQL.
Большая разница клиентского и серверного времени требует проверки сети,
прокси и обработки ответа. Она не равна чистому сетевому времени. Разница между
screenData и screenFrame показывает ожидание следующего кадра; Flutter DevTools
нужен для разбора перерисовок и растеризации.

## Инварианты

Контекст сервера использует AsyncLocalStorage.run и изолирован между запросами.
После HTTP finish/close отложенная работа не увеличивает закрытые счётчики.
Контекст Flutter использует Zone; независимые операции не смешиваются.

SQL, параметры, ответы, URL-параметры, имена клиентов и токены не добавляются в
новые измерения. На сервере логируется шаблон зарегистрированного маршрута, для
неизвестного пути — unmatched. Старые exception logs не изменены этим этапом.
Server-Timing и X-Request-Id доступны Flutter Web через CORS exposed headers.

Транзакции используют одно соединение. Временная обёртка query не изменяет
экземпляр клиента в пуле; callback/stream overloads сохраняются и не измеряются.
При ошибке rollback соединение исключается из пула, исходная ошибка сохраняется.
Фоновые задания вне HTTP-контекста не покрываются этими счётчиками. Размер пула,
бизнес-правила, схема БД и настройки production не менялись.

Основания: [Node.js AsyncLocalStorage](https://nodejs.org/api/async_context.html),
[node-postgres: транзакции](https://node-postgres.com/features/transactions),
[Flutter: профиль производительности](https://docs.flutter.dev/tools/devtools/performance).
