# Оптимизация SQL и бюджета соединений

## Сбор статистики без изменения БД

Из каталога `server`, с явно заданным адресом базы:

```powershell
$env:DATABASE_DIAGNOSTICS_URL = '<явно выбранная строка подключения>'
npx ts-node scripts/inspect-database-performance.ts
```

Скрипт выполняет транзакцию read only с statement_timeout 5 секунд, читает размеры
таблиц/индексов, счётчики сканирования, даты analyze/vacuum и stats_reset. Если
pg_stat_statements доступен, выводит 20 queryid по суммарному времени выполнения,
число вызовов и обращения к буферам. SQL-текст, параметры и строки бизнес-таблиц
не выводятся. Статистика не сбрасывается, расширения не устанавливаются.

pg_stat_statements требует предварительной загрузки модуля и установки расширения
в выбранной базе. Если этого нет, скрипт явно возвращает not_enabled. Изменение
настроек PostgreSQL с перезапуском не входит в диагностику. Отсутствующий счётчик
не означает нулевую нагрузку; idx_scan=0 не доказывает ненужность индекса.
Статистику следует оценивать за репрезентативный интервал после stats_reset.

## Воспроизводимый локальный benchmark

```powershell
$env:V4_PLATFORM_TEST_DATABASE_URL = '<адрес изолированной localhost-базы audit_fix>'
npx ts-node scripts/benchmark-schedule-reads.ts
```

Скрипт отказывается работать вне localhost и базы с audit_fix в имени.
Он использует настоящие SQL-запросы ScheduleReadService: матрицу расписания и
список занятий ученика. Только таблицы lessons/lesson_reservations заменяются
в запросе временными клонами с текущими ограничениями и исходными индексами.
Остальные joins и SQL-проверки текущей роли сохраняются. Синтетический actor
создаётся внутри транзакции и откатывается вместе с ней.

Набор содержит 60000 занятий за 365 дней, 500 учеников, 40 учителей/аудиторий,
10% отменённых занятий и четыре записи резерва на занятие. Это контролируемый
сценарий, не копия production и не утверждение о его распределении данных.
Финансовые исторические таблицы не заполняются массово этим benchmark.

После прогрева выполняются пять EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) для каждого
варианта: исходный запрос и индексы; только новый индекс; индекс и новый запрос
фильтрации ученика. Исходный коррелированный предикат восстанавливается явно,
а актуальный SQL берётся из сервиса. Дополнительно сравниваются SHA-256 полных результатов запросов,
включая порядок. Все бизнес-данные benchmark откатываются. Если миграция уже
применена, новый индекс удаляется только из TEMP-клона для воспроизведения
исходного варианта. Планы сохраняются в outputs/application-audit-2026-09-05.

Это время выполнения SQL без сети и отрисовки экрана. Последовательность прогонов
может влиять на кэш; цифры не являются обещанием такого же ускорения production.

## Фильтрация занятий ученика

В listLessons коррелированный EXISTS по group_students заменён на проверку
group_id = ANY(ARRAY(...)): действующие группы выбранного ученика вычисляются
один раз. На контрольном наборе прежний вариант проверял участие почти для
каждого из 60000 занятий; новый позволяет использовать индексы занятий.

Сохраняются индивидуальные занятия и занятия действующих групп; left_at IS NULL
остаётся обязательным условием участия. Ограничения роли, филиала и остальные
фильтры применяются прежним SQL. Отдельный PostgreSQL-тест сравнивает полные
результаты старого и нового предикатов для активного участия, выхода из группы,
другого ученика, пустого результата и запроса без фильтра ученика. Проверяется
также понижение роли в БД при устаревшей роли director в токене.

## Индекс 0153

lesson_reservations_current_read_idx соответствует существующему чтению:
lesson_id, затем приоритет state='reserved', updated_at DESC, id DESC. State
включён в индекс для покрытия выдаваемого поля. Ранее эта lateral-выборка могла
читать и сортировать несколько записей истории для каждого занятия; теперь
может остановиться на первой подходящей записи индекса.

Порядок приоритетов, история резервов, ограничения и SQL-авторизация не меняются.
Издержка — дополнительное место и обслуживание одного B-tree при записях.
Второй экспериментальный индекс сортировки lessons не дал устойчивого выигрыша
для матрицы и в миграцию не включён.

Миграция запускается обычным MigrationRunner внутри транзакции. Это CREATE INDEX,
поэтому построение временно блокирует записи в lesson_reservations; CONCURRENTLY
не используется внутри транзакции. lock_timeout=5s ограничивает ожидание блокировки,
statement_timeout=2min ограничивает построение. Для выпуска требуется измерить
длительность на актуальном объёме и выбрать окно обслуживания. Production/deploy
по-прежнему требуют прямой команды владельца, backup и проверки отката.
Down удаляет только этот индекс; бизнес-факты остаются нетронутыми.

## Бюджет соединений

DATABASE_POOL_MAX задаёт предел одного экземпляра DatabaseService: целое 1–50,
по умолчанию 10. Значение проверяется при старте приложения и в конструкторе
сервиса для инструментов вне AppModule. Бюджет PostgreSQL должен учитывать
сумму пулов всех процессов/реплик, фоновые задания и резерв администрирования.

Увеличение пула само по себе не ускоряет SQL и может усилить конкуренцию. Сначала
сопоставить dbAcquireMs и dbQueryMs, нагрузку БД и запросы с большим суммарным
временем. Значения рабочих окружений этим этапом не менялись.

Источники: [pg_stat_statements PostgreSQL 17](https://www.postgresql.org/docs/17/pgstatstatements.html),
[индексы и ORDER BY/LIMIT](https://www.postgresql.org/docs/17/indexes-ordering.html),
[CREATE INDEX и блокировки](https://www.postgresql.org/docs/17/sql-createindex.html).
