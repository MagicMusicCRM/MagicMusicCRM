# Сценарии сотрудника и восстановление данных

## Запуск

Полная существующая production-like проверка теперь включает UI и восстановление
синтетической резервной копии. Из корня проекта на Windows:

```powershell
npm --prefix server run build
./scripts/v7_production_like_gate.ps1 -DatabaseName ('magiccrm_v7_prodlike_employee_' + [guid]::NewGuid().ToString('N'))
```

Отдельный повтор сценариев без production-like readiness:

```powershell
node scripts/http-journey-check.cjs --release-journeys
```

Существующие 22 HTTP-сценария остаются обязательными. Новый режим дополнительно
запускает `integration_test/employee_journey_live_test.dart` на Windows и сверяет
результат напрямую с PostgreSQL. Отсутствие fixture, UI-checkpoint, неуспешный
Flutter exit, финансовое расхождение или ошибка restore дают ненулевой код.
Неизвестные флаги отклоняются. `-ServerOnly` у production-like gate явно отмечает
неполное покрытие; это не подтверждение полного выпуска.

## Что проходит через интерфейс

Реальный логин выдаёт сессию синтетического Director. Продуктовые формы и карточки
используют Riverpod, MagicCrmService, Dio, настоящий AppModule и новую локальную БД.
Тест не подменяет ответы HTTP. Контролируемая потеря успешного ответа оплаты
имитирует обрыв соединения после commit; push-соединение отключено, чтобы проверить
сохранение и конфликт при недоступной доставке realtime.

| Действие | Проверяемый результат |
| --- | --- |
| Создать ученика | Форма закрылась; новая карточка читает сохранённого ученика |
| Внести 5000 ₽, дважды нажать, потерять ответ и повторить | Черновик и ошибка видны; один запрос до retry; retry использует прежний ключ; один платёж и событие статуса |
| Записать на занятие за 1500 ₽ и дождаться расчёта | Worker применяет сохранённый план; лента показывает «Завершено»; баланс 3500 ₽; одно списание и начисление преподавателю |
| Отменить следующее занятие и вернуть остаток | Подписанный preview/commit; лента показывает «Отменено»; отмена не списывает деньги; один возврат 3500 ₽; баланс 0 ₽ |
| Изменить ученика из двух открытых карточек | Первый текст сохранён; второй получает конфликт и сохраняет черновик; повторное открытие показывает серверный текст |

Обычное занятие не завершается ручной командой: это действующее продуктовое
правило. Тест создаёт уже закончившееся занятие через форму и дожидается настоящего
completion worker. Другое, будущее занятие отменяется через действующий редактор.

Девять контрольных точек сохраняют screenshots и `employee-result.json`.
Проверка БД подтверждает число оплат, возвратов, занятий, финансовых фактов,
payment history и audit. Состояние повторно проверяется после восстановления.

Это native Windows integration build с настоящими продуктовыми поверхностями,
открытыми тестовым launcher. Логин вводится через API; обход меню всего приложения,
установка Release-пакета, Android, остальные роли и доставка realtime этим
набором не проверяются. Он дополняет существующие device/role/image/package gates.
Число HTTP-запросов в основном отчёте относится к прежним HTTP-сценариям;
UI-запросы находятся в отдельном логе настоящего API.

## Два вида восстановления

Синтетическая копия создаётся `pg_dump --format=custom` после остановки API/worker.
`pg_restore --exit-on-error` восстанавливает её в случайную новую localhost-БД.
Сравниваются SHA-256 всех строк каждой из таблиц `app`, количества и финансовая
сверка; после этого удаляются только БД/дамп, созданные текущим запуском.
В evidence сохраняются имена таблиц, количества и хеши, без строк данных.

Реальная зашифрованная копия проверяется отдельно существующим
`infra/scripts/verify-release-backup-compatibility.sh`:

```powershell
./scripts/check-encrypted-backup.ps1 `
  -CandidateImage magicmusiccrm-server:1.5.31-211-final `
  -RollbackImage magicmusiccrm-server:1.5.30-210-hotfix1-89c3c36f `
  -ExpectedMigrationId 0149_lesson_settlement_policy_revision
```

Это пример для реально проверенных локальных образов, а не выбор образов для
следующего deploy. При выпуске подставляются точные candidate/rollback и head
миграции candidate. Обёртка читает labels и фиксирует image ID.
По умолчанию выбирается последний по имени `.tgz.enc` с `.sha256` в `dist/backups`.
Можно явно передать `-BackupPath`, `-BackupSecretFile`, `-EvidencePath`.

Для Windows собирается отдельный Docker-образ инструментов, запускающий прежний
скрипт. У него нет внешней сети; он управляет только временными ресурсами drill
через локальный Docker socket. Архив и исходный файл секрета подключены read-only.
Только строка ключа передаётся строгому парсеру в приватном tmpfs; конфигурация
не исполняется, ключ не попадает в команды/логи. Сетевые зависимости нужны только
при сборке образа инструментов. Данные восстановления остаются в новой внутренней
Docker-сети и новом временном volume; production Compose не вызывается.

Сам скрипт проверяет checksum/decryption, архив, restore, candidate migration,
reconciliation и совместимость rollback со схемой candidate. Логи этого режима
не содержат восстановленные строки и находятся в `dist/backup-drills/<run>/`.

## Регулярность и статус

В Codex включена еженедельная проверка по понедельникам в 09:00, Europe/Moscow
(автоматизация `magicmusiccrm`). Она запускает синтетический restore и проверку
самой свежей доступной зашифрованной копии. Нужны доступный локальный host, Docker,
PostgreSQL toolchain и подходящие локальные образы. Сбой, отсутствие образа или
копия старше 7 суток требуют действия; неизменные уведомления не повторяются.
Это локальная автоматизация Codex, а не установленный production cron.

2026-09-05 реальный архив `magicmusiccrm-staging-20260829T130201Z.tgz.enc`
успешно восстановлен с candidate 211 / rollback 210-hotfix.1 / schema 0149.
Evidence: `dist/backup-drills/12275227a57a47b2ac396c767d35a9c0/`.
Копии около 7 суток: PASS доказывает её восстановимость, но не актуальность
резервирования production. Свежая копия в рамках этой задачи не создавалась.

Общий отчёт UI/HTTP содержит HEAD и SHA-256 проверяемых исходников, включая
незакоммиченные изменения. Изменение исходников во время проверки отвергает PASS.
Новый checkout требует новый прогон; этот результат не подтверждает будущий image.

возвращает contact_email, который читает финальная SQL-проекция. Регрессия создания
с email и без него проверяется на PostgreSQL вместе с существующими student-тестами.
