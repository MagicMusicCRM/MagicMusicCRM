# Проверяемые контракты расходов и оплат

Контракт покрывает GET/POST /api/crm/expenses и PATCH/DELETE /api/crm/expenses/{id}.
Источник — текущий CrmFinanceController и DTO с метаданными @nestjs/swagger.
Ответы контроллера типизированы; TypeScript проверяет совместимость с результатами
существующего финансового сервиса. Отдельных бизнес-моделей или API-клиентов нет.

Дополнительно покрыты POST /api/crm/students/{studentId}/payment-records и
POST /api/crm/students/{studentId}/payment-records/{paymentRecordId}/transition.
Также покрыты POST-команды correction/preview, correction, reversal/preview и
reversal под /api/crm/students/{studentId}/payment-records/{paymentRecordId}.
Источник всех шести операций — SubscriptionCommerceController и действующие DTO.
Команды абонементов и самостоятельных корректировок счёта пока не включены.

## Запуск проверки

Из корня репозитория, без обращения к БД:

```powershell
./scripts/check-api-contracts.ps1 -Offline
```

Полная проверка требует уже мигрированную изолированную localhost-базу с audit_fix
в имени. Синтетические команды записывают финансовую историю в этой тестовой БД:

```powershell
$env:V4_PLATFORM_TEST_DATABASE_URL = '<адрес изолированной localhost-базы audit_fix>'
./scripts/check-api-contracts.ps1
```

Скрипт прерывается при ошибке. Полный режим не заменяет отсутствующую проверку
PostgreSQL пропуском; для пропуска требуется явный -Offline. Production URL
и автоматическая загрузка .env не используются. Сетевой HTTP-сервер теста
слушает только 127.0.0.1 на свободном порту.

## Что проверяется

1. contracts/expenses.openapi.json точно совпадает с экспортом актуального кода.
2. Flutter MagicCrmService через настоящий MagicApiClient/Dio сериализует запросы
   в согласованные JSON, HTTP-методы, URL и query. Проверяются заголовки команд,
   сохранение переданной identity и чтение общих ответов.
3. Общие примеры contracts/expenses.fixtures.json соответствуют OpenAPI и
   реальному ValidationPipe. Проверка специально отвергает потерю expectedVersion,
   неизвестное поле и неправильный тип/дату ответа.
4. HTTP/PostgreSQL проходит CRUD, повтор исходной команды после изменения/удаления,
   cursor-пагинацию и сохранение общего итога; проверяются ошибки 400/403/409 и
   три неизменяемые ревизии исходного расхода. Отдельно проверяется envelope 401.

В HTTP-наборе используется настоящий контроллер, DTO, ExpenseService,
PlatformIntegrityService и PostgreSQL. Harness подставляет identity вместо
JWT-проверки и подключает ExpenseService к зависимостям контроллера. Это не
проверка логина, полного AppModule, интерфейса расходов или других API-доменов.
Пять Flutter-сценариев используют транспортный адаптер с синтетическими ответами.
Они проверяют точные wire-данные, а не взаимодействие Flutter с живым сервером.

Схема описывает формат обмена; все бизнес-проверки и RBAC остаются на сервере.
Даты во входных DTO сохраняют существующий ISO 8601 контракт, включая дату без
времени; выходные даты имеют формат date-time. Необязательное поле и null не
считаются взаимозаменяемыми автоматически. Суммы расходов остаются числами в
рублях, без изменения финансовой модели.

## Изменение API

После согласованного изменения DTO/ответа выполнить из server:

```powershell
npm run contract:export
npm run contract:payments:export
```

Затем проверить diff JSON и адаптировать клиент/примеры по реальному сценарию.
Не перегенерировать артефакт только ради зелёного contract:check: переименование
или удаление поля может требовать совместимого перехода клиента и сервера.
Готовую команду проверки можно подключить к CI; подключение к внешнему CI этим
этапом не выполнялось. Генератор не запускает AppModule, БД, workers или Swagger UI.

Production-сборка ограничена src через tsconfig.build.json. Служебные TS-скрипты
остаются доступны для typecheck/ts-node, но не сдвигают runtime entrypoint:
команды запуска сохраняют dist/main.js и dist/db/migrate.js.

## Оплаты: повтор команды и версия ответа

Контракт payments.openapi.json описывает amountMinor как строку целых копеек,
статусы unpaid/posted_pending/paid, обязательную expectedVersion для смены статуса
и Idempotency-Key для команд. Подтверждение оплаты дополнительно требует способ,
номер операции/чека, дату поступления и филиал в карточке ученика; эти зависимости
продолжает проверять PaymentLifecycleService с ошибкой 422.

Повтор команды сохраняет её единственный финансовый эффект, но ответ читает
текущее состояние оплаты. Например, повтор создания unpaid после подтверждения
возвращает paid с версией 3. Ранее этот путь возвращал paid с версией 1 исходной
команды. Теперь версия берётся из той же записи, что и остальные поля ответа.
События истории, появившиеся после чтения этой записи, в ответ не включаются.
Это не исторический снимок первоначального ответа и не новый event store.

Три общих примера payments.fixtures.json проверяют фактическую сериализацию Dio
и чтение ответов Flutter. HTTP/PostgreSQL-набор проверяет цепочку unpaid →
posted_pending → paid, повтор каждого шага после подтверждения, единственный
фактический платёж и три события истории. Дополнительно проверяются устаревшая
версия, изменённый payload с прежним ключом, чужой ученик, запрещённая роль и
смена роли в БД при устаревшей роли director в запросе. JWT identity и доставка
realtime заменены harness; финансовые сервисы, репозитории, audit/outbox и БД
используются настоящие. Отдельный unit-тест воспроизводит гонку чтения истории.

Проверка расходов сохранена. Её прежняя команда check-expense-contract.ps1
по-прежнему доступна отдельно; check-api-contracts.ps1 проверяет оба домена.
Экспорт схем по тегам, проверка wire-формата и envelope ошибок общие.

Предыдущий этап, 2026-09-05: 24 серверных теста общего contract gate, 163 серверных
регрессионных теста и 8 Flutter-тестов; typecheck, build и анализ двух Dart-тестов
успешны. Логи: outputs/application-audit-2026-09-05/payment-contract-gate.txt и
payment-backend-regression.txt. Production не изменялся, новых миграций нет.

## Коррекция и отмена оплаты

Предпросмотр возвращает подписанный previewToken, ожидаемую версию, срок действия
и изменение баланса без записи финансовых фактов. Подтверждение передаёт этот
токен, confirm=true, причину и Idempotency-Key. Версия и рассчитанные условия
проверяются существующими сервисами. Суммы передаются строками целых копеек;
изменение и итог баланса могут быть отрицательными. Это не меняет запрет перевода
между учениками сверх доступного остатка.

Четыре примера payment-adjustments.fixtures.json проверяются схемой, ValidationPipe
и настоящим Flutter/Dio транспортом с синтетическими ответами. HTTP-набор использует
настоящие PaymentCorrectionService, PaymentReversalService, подписывание токенов
и PostgreSQL. Проверяются коррекция подтверждённой суммы, денежная отмена,
техническая отмена неоплаченной записи, повтор команды без дублей, подмена/истечение
токена, привязка к записи, устаревшая версия и изменение баланса после preview.
Исходные платежи сохраняются; компенсирующие факты добавляются отдельно.

Этот набор выявил потерю correction.id в реальном HTTP-ответе: SQL возвращал id,
а сервис читал correction_id. Репозиторий теперь явно возвращает id as correction_id
при создании и повторном чтении корректировки; тест сверяет ответ с сохранённым id.
Повтор коррекции/отмены сохраняет исторический результат соответствующей команды;
правило текущего ответа PaymentLifecycleService на них не распространяется.

CommerceProjectionRepository сверяет выбранную по identity роль с актуальной
ролью неудалённого пользователя в БД внутри запроса scope. Устаревшая identity
не открывает предпросмотр или расширенный scope после смены роли. Проверка не
добавляет отдельного SQL-вызова и сохраняет ограничения семьи/филиала. HTTP-тест
воспроизводит director → teacher при прежней identity; JWT guard заменён harness,
поэтому это проверка защиты сервисного слоя, а не полного процесса авторизации.

Проверено для этого расширения 2026-09-05: 32 серверных теста общего contract gate,
1466 серверных регрессионных тестов (включая параметризованные проверки токенов),
12 Flutter-тестов; typecheck, build и анализ нового Dart-теста успешны.
Логи: outputs/application-audit-2026-09-05/payment-adjustment-gate.txt и
payment-adjustment-regression.txt. Production не изменялся, новых миграций нет.

Основа экспорта: [NestJS OpenAPI](https://docs.nestjs.com/openapi/introduction) и
[метаданные DTO](https://docs.nestjs.com/openapi/types-and-parameters).
Форматы ответов проверяются [Ajv с ajv-formats](https://ajv.js.org/guide/formats.html).
