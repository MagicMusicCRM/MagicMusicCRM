# Контроль применённых миграций

`MigrationRunner` сохраняет SHA-256 пары up/down SQL при применении миграции.
Перед up/down проверяется весь применённый набор: отсутствие файла или изменение
SQL останавливает выполнение. CRLF нормализуется в LF; остальные байты участвуют
в контрольной сумме. Исправления схемы оформляются новой миграцией.

## Переход существующей установки

Старые строки журнала не содержат SQL, поэтому восстановить фактическую историю
по текущим файлам невозможно. Автоматического доверия этим файлам нет: up/down
остановятся с `Legacy migration checksum baseline required`.

1. Получить SQL из проверенного артефакта ранее установленного релиза, сопоставить
   его с журналом установки и схемой БД. При расхождении сначала восстановить
   проверяемую историю; не подавлять ошибку новым хешем изменённого файла.
2. Из каталога `server` получить манифест этого набора:
   `node dist/db/migrate.js manifest`. Сохранить JSON в проверяемый файл вне Git,
   вместе с идентификатором релиза и результатом сверки.
3. В согласованное окно выпуска после backup выполнить
   `node dist/db/migrate.js baseline <reviewed-manifest.json>`, затем обычный up.
   Требуется `MIGRATION_DATABASE_URL` с правами владельца миграций.
4. Проверить `checksum_origin`: старые строки имеют `legacy_baseline`, новые —
   `applied`. Baseline не доказывает, что эти байты исполнялись исторически,
   и не позволяет заменить уже сохранённый несовпадающий хеш.
5. Выполнить post-deploy reconciliation по плану выпуска. Для миграций с новыми
   финансовыми фактами простой down может намеренно запрещаться: нужен отдельный
   проверенный план восстановления или исправления вперёд.

Production baseline и deploy требуют прямой команды владельца согласно AGENTS.md.
Локальный манифест из `outputs/application-audit-2026-09-05` относится только к
изолированной тестовой БД этой проверки и не является production baseline.
