# Автоматические проверки пользовательских сценариев

Последний прогон после исправления: **24 PASS / 0 FAIL**, 0 ответов 5xx.
Подробности и границы проверки — ниже, в разделе «Исправление».

Из корня репозитория:

```powershell
npm --prefix server run test:journeys
npm --prefix server run test:journeys -- --windows
```

Первый вариант запускает настоящий NestJS API и отправляет HTTP-запросы.
Второй дополнительно запускает Windows UI: настоящая форма создания занятия
сохраняет его через тот же API, затем в PostgreSQL проверяются запись,
плательщик, цена и стандартное правило оплаты преподавателю.
Также выполняется отдельный набор из пяти UI-сценариев с управляемыми ответами
API. Эти пять сценариев не считаются сквозной проверкой сервера.

Нужны установленные `server/node_modules`, локальная PostgreSQL на 54329 и,
для `--windows`, Windows toolchain с Flutter в `C:/Flutter`. Можно задать
`HTTP_JOURNEY_ADMIN_URL`, но разрешены только loopback и maintenance DB
`postgres`. Программа создаёт отдельную БД со случайным именем, применяет
миграции, создаёт синтетические справочники/пользователей/существующие абонементы.
По окончании удаляется только эта созданная БД; существующие базы не очищаются.

API запускается из пустого рабочего каталога с отдельным окружением,
без загрузки `server/.env`. У тестового оператора случайный пароль, обычный
HTTP login и действующие серверные проверки прав. Предусмотренное приложением
исключение OTP ограничено адресом этого временного локального оператора.
В Windows токены находятся в памяти, пользовательское хранилище входа не меняется.
Production API и production-данные не используются.

## Проверяемые сценарии

- Авторизация, валидация обязательных/пустых значений, неверные идентификаторы.
- Создание отдельного занятия и постоянного расписания на весь диапазон
  сентябрь–декабрь; повтор создания не добавляет дубликаты; абонемент на 12
  покрывает 12 занятий, оставшиеся создаются без покрытия.
- Изменение преподавателя/аудитории, редактирование непокрытого занятия,
  другой плательщик, личный счёт, скидка/надбавка, другой абонемент и возврат
  к первоначальному. Предпросмотр сохраняет резервы, снимки и финансовые факты.
- Повторное подтверждение, устаревшая версия и два одновременных подтверждения;
  назначенные занятия не создают фактические списания/начисления.
- Сохранение и очистка заметки через PATCH: повтор запроса не дублирует audit/outbox,
  остальные данные занятия и план расчёта остаются прежними.
- Windows: создание с личным счётом через настоящую форму/API/БД; отдельные UI-проверки
  оплаты, источника средств, предварительного расчёта и группового расчёта.

## Результат и ограничения

`dist/http-journeys/<run-id>/result.json` содержит PASS/FAIL каждого сценария,
число запросов самого HTTP-runner и число полученных им 5xx. Запросы Windows
не входят в этот счётчик. `api.log`, `windows.log`, `windows-forms.log`
и PNG-снимки лежат рядом.
Ненулевой код завершения означает ошибку сценария или подготовки; это не PASS.
Сбой одного независимого сценария не скрывает результаты остальных.

Фоновые workers выключены, поэтому этот прогон не проверяет автозавершение,
рассылки и обработку outbox. Абонементы создаются как существующие тестовые
записи: продажа, возврат, выплата преподавателю и полная миграция production
данных этим прогоном не проверяются. Windows использует Debug-сборку и реальные
виджеты продукта; это не проверка всего приложения или всех ролей.

Первое выполнение 03.09.2026 обнаружило два 500 при `label=null` и
`displayName=null`, а также отказ 422 при PATCH только заметки занятия.
Причина последнего: `ValidationPipe` создаёт экземпляр DTO с собственными
полями `undefined`, а `assertLessonPatchUsesTransition` проверяет `Object.keys`
без проверки наличия значения. Эти ошибки были воспроизведены до изменения
продукта; ожидания тестов не заменялись ошибочными ответами.

## Исправление, 03.09.2026

DTO обновления источника и дополнительного поля теперь различают отсутствие
поля и явный `null`: `canonicalName`, `displayName`, `label` можно не передавать,
но переданный `null` отклоняется с HTTP 400 до команды. Это также закрывает
вызов `.trim()` на null при проверке системного источника.

Guard заметки игнорирует только поля со значением `undefined`, добавляемые
экземпляром DTO. Переданные защищённые значения, включая `null`, `false` и `0`,
по-прежнему требуют специальной команды изменения занятия. Заметку можно
сохранить или очистить без изменения ресурсов и расчёта; существующие version,
idempotency, audit и outbox остаются в каноническом пути команды.

Перед исправлением новые проверки воспроизвели шесть отказов; после исправления
четыре релевантных Jest-набора прошли: 54 теста. `npm --prefix server run build`
завершился успешно. HTTP-прогон `6e01314e4c124964b33eeb7fefe94deb`:
22 PASS, 0 FAIL, 43 запроса, 0 ответов 5xx.
