# Magic Music CRM — «Клиенты» + Управленческая аналитика

**Дизайн-спецификация · 2026-06-19**
Ветка: `s8-desktop-ux-stabilization` · Платформа: Flutter (Windows desktop + Android), NestJS + PostgreSQL.

---

## 0. Цель

Превратить экран «Лиды» в полноценный модуль **«Клиенты»** с двумя настраиваемыми канбанами
(воронка лидов + ученики по филиалам/направлениям), навести порядок в данных (телефоны,
дубли, семьи, филиалы, дисциплины), достроить недостающие данные из HolliHop и добавить
управленческую аналитику для администратора/собственника школы — с UX, не требующим лишних
действий.

Программа разбита на **6 эпиков** (A–F). A и E — фундамент; C и F дают видимую ценность.
Каждый эпик при реализации получает свой implementation-plan (skill `writing-plans`).

## 1. Реальность данных (прод, на 2026-06-19)

Замеры на боевой БД `magiccrm` (`api.phantom-net.ru`):

| Сигнал | Значение | Следствие |
|---|---|---|
| Лиды всего / без статуса | 3683 / 446 | 446 «Без статуса» → «Новый» |
| Колонки Контакт/Переговоры/Договор | 0 / 0 / 0 лидов | удалить безопасно |
| Ученики / филиалы | 1955 / 2 (Сокол, Спортивная) | 2 доски учеников |
| Ученики с филиалом / дисциплиной | 0 / 1 из 1955 | branch+discipline не импортированы — блок доски «Ученики» |
| Ученики со связью с лидом | 1 из 1955 | lead↔student связь отсутствует |
| Телефоны валидны RU-11 (лиды/профили) | 2981 / 823 | нормализуются чисто |
| Телефоны без кода страны `9XXXXXXXXXX` | 647 / 205 | префикс +7 безопасно |
| Телефоны мусор/пустые | 22+33 / 19+99 | маленькая очередь ревью |
| Группы лидов с общим номером | 1676 (3440 строк) | **в основном семьи, не дубли** |
| …из них группы с РАЗНЫМИ именами | **1675 из 1676** | один номер на семью |
| Лиды с номером существующего ученика | 1920 | конвертированные клиенты в воронке |
| Номера, общие для ≥2 учеников | 27 (55 учеников) | явные семьи |

**Ключевой вывод:** телефон в этой базе — идентификатор **семьи**, а не человека. Поэтому
дедуп строится по **номер + имя** (истинных дублей ≈ 1), а общий номер при разных именах
становится **семейной** связью, а не слиянием.

## 2. Лог решений (утверждено пользователем)

1. Окно «Клиенты» = сегмент-переключатель **Лиды / Ученики**; drag карточки лида во вкладку
   «Ученики» = конвертация лид→ученик с выбором филиала и направления.
2. Дисциплины/направления — **полноценные сущности** (`disciplines`, `branch_disciplines`,
   `student_disciplines`), не свободный текст.
3. Телефоны — единая нормализация к `+7 (XXX) XXX XX XX`; нераспознаваемые → очередь ревью
   (не угадывать).
4. Дедуп — очередь слияния с подтверждением админа; **никаких тихих автослияний**.
5. 1920 конвертированных лидов — связать с учеником (по **номер+имя**) и убрать с доски «Лиды».
6. Терминальные «Успешный»/«Отказ» — свёрнутый «Архив» справа.
7. Авто-лиды из чата — `source='Через приложение'` + бейдж на карточке.
8. Реимпорт HolliHop — есть живой API-ключ; план dry-run → отчёт → apply после бэкапа.
9. **Семьи** — отдельная фича; номер = ключ семьи, каждая карточка остаётся отдельной;
   переход родитель↔ребёнок в 1 клик. **Плательщик-родитель = полноценная персона**
   (своя карточка, телефон, история платежей, роль `payer`).
10. Ученик с несколькими направлениями — вводим **основное направление** (`is_primary`):
    в канбане ученик в колонке основного направления, остальные — в карточке.

## 3. Архитектура: три фундамента

Аудит 20 областей отчётности показал, что 17 из них блокируются тремя примитивами.
Их делаем **до** отчётов.

### F1. Единый `branch_id` (FK)
Сейчас филиал лежит в `custom_data->>'branchId'` только у лидов/учеников; у платежей,
расходов, задач, чатов — отсутствует. Любая аналитика «по филиалам» невозможна.
→ Добавить `branch_id uuid REFERENCES app.branches(id)` на `leads`, `students`, `payments`,
`expenses`, `tasks`, `chats`; бэкофилл; частичный индекс `(branch_id) WHERE deleted_at IS NULL`;
синхронизация с `custom_data` на период перехода.

### F2. `lead_status_history` — событийная таблица переходов
Сейчас `updateLead` пишет пустой audit-row без old/new (`crm.service.ts:4245`) — прошлое
невосстановимо. Это keystone воронки, истории статусов, истории ответственных и таймстампов SLA.
→ Одна таблица фиксирует переходы **и статуса, и ответственного** (не дублировать инфраструктуру).

### F3. Аналитический слой
Матвью нет; `getFinanceReport`/`getManagerDashboard` гоняют тяжёлый live-SQL на каждый запрос.
→ Snapshot-таблицы + materialized views + refresh-воркер. Воркер — на **существующем паттерне**
`notification-worker.service.ts` (setInterval + DB-claim), идемпотентность как у `lesson_reminders`.
**Не добавлять** Bull / @nestjs/schedule.

**Принцип UX всей программы:** не плодить экраны, а наполнять существующие
(`ReportsWidget`, `ManagerOverviewWidget`, `FinancialDashboardWidget`, `schedule_widget`,
`tasks_widget`, `lead_detail_dialog`). Меньше навигации — привычный workflow менеджера.

## 4. Эпики

### Эпик A — Data Foundation

Бедрок для UI и аналитики. Включает телефоны, Семьи, F1, F2, словари.

**A1. Нормализация телефонов.**
Единая функция `normalizePhoneRu()` заменяет три расходящиеся (`profile`/`crm`/`import`).
Хранение: канонический `+7XXXXXXXXXX`; отображение — маска `+7 (XXX) XXX XX XX`.
- Колонка `phone_normalized text` на `app.leads`, `app.profiles` (+ B-tree индекс).
- Бэкофилл-миграция: `9XXXXXXXXXX` → префикс +7; нераспознаваемое → очередь.
- `app.phone_review_queue(id, entity_type, entity_id, raw_phone, reason, created_at, resolved_at, resolved_by)`.
- Flutter: маск-форматтер `+7 (###) ### ## ##`, валидация 11 цифр, escape-hatch «международный номер».
- Очередь ревью видна управляющему (счётчик/бейдж).

**A2. Семьи.**
```
app.families(id, name, branch_id→branches, primary_payer_member_id, created_at, updated_at, deleted_at)
app.family_members(id, family_id→families,
  entity_type text /* 'student'|'lead'|'profile' */, entity_id uuid,
  role text /* parent|child|partner|sibling|guardian|payer */,
  is_primary_contact bool, created_at,
  unique(family_id, entity_type, entity_id))
app.contacts(id, entity_type, entity_id, phone_normalized, name, role, created_at)  -- из HolliHop Agents[]
```
- Плательщик-родитель заводится как полноценная персона (profile/карточка).
- Предложения семей сидятся из общего нормализованного номера (1675 групп) и `app.duplicate_candidates`;
  27 «мультиученических» номеров — явные семьи.
- UX: блок «Семья» в карточке; в карточке ребёнка — чип родителя (1 клик), в карточке родителя —
  список детей/партнёров (1 клик в каждого); бейдж семьи на канбан-карточке; роль `payer`
  связывает финансы.

**A3. Единый `branch_id` (F1).** См. §3. Бэкофилл: leads/students из `custom_data`;
payments/tasks — через связанную сущность; expenses — ручной/дефолтный филиал. На `chats`
дополнительно `lead_id`, `student_id` (для SLA-разрезов).

**A4. `lead_status_history` (F2).**
```
app.lead_status_history(id, lead_id→leads,
  old_status_id, new_status_id, old_owner_id, new_owner_id,
  changed_by, changed_at, reason_id→lead_loss_reasons NULL,
  comment text, branch_id, source_snapshot text)
index (lead_id, changed_at desc)
```
Запись на каждое изменение `status_id`/`assigned_to` в `updateLead` (на стороне сервиса).
Параллельно `app.student_status_history(student_id, status, branch_id, changed_at)` для когорт
retention (lost/reactivated).

**A5. Словари.**
- `app.lead_loss_reasons(id, name, kind 'lost'|'paused', sort_order, is_active, color)`;
  на `lead_statuses` добавить `is_terminal`/`requires_reason`; `updateLead` требует `reason_id`
  при переходе в терминальный статус.
- `app.lead_sources(id, canonical_name, display_name, is_active)`; UTM-колонки на `leads`
  (`utm_source/medium/campaign/content/term`, `referrer`, `first/last_touch_source/at`) — P2.
- `app.disciplines(id, name, is_active)`, `app.branch_disciplines(branch_id, discipline_id, sort_order)`,
  `app.student_disciplines(student_id, discipline_id, is_primary)`.

### Эпик B — Реимпорт HolliHop

Усиление **существующего** импортёра (`server/src/migration/hollihop-import.ts`), не переписывание.
Живой API-ключ есть. План: dry-run → gap-отчёт → apply после `pg_dump`.

- `GetStudentLogs/LeadLogs/SystemLogs` + `GetComments` — из «optional» в обязательные;
  писать в историю действий (`app.activity_log`) и комментарии.

### Эпик D — UX-полировка

- **Поиск в реальном времени:** не сбрасывать доску в skeleton при рефетче — держать прежние

- **Back + сохранение состояния:** скролл и фильтры при возврате из карточки.
- **Empty states** везде; **reduced-motion** для анимации переноса.

## 5. Последовательность

```
A (Data Foundation)
├─ B (HolliHop reimport)   ── наполняет данные для F
└─ E (Analytics platform)
        │
        ├─ C (Окно «Клиенты»)   ── видимая ценность для менеджера
        └─ F (Reporting волнами P0→P1→P2)
                 │
                 └─ D (UX-полировка)   ── поверх C
```
A и E — фундамент (можно частично параллельно). B зависит от A (чистая линковка).
C пишет переходы в F2 и использует F1. F строится на A+E. D наслаивается на C.

Параллельно продолжаются мобильные P1-фиксы KVA-167–175 (не конфликтуют).

## 6. Риски

- **Реимпорт на боевой БД** (1955 учеников, 3683 лида): обязательный `pg_dump` до apply;
  dry-run + diff-отчёт; запуск в нерабочее время.
- **Бэкофилл `branch_id`**: держать `custom_data` в синхроне до полного перехода; NOT NULL только
  после проверки бэкофилла отчётом качества данных (#16 как QA-инструмент).
- **Скрытие конвертированных лидов**: строго по номер+имя (не по одному номеру) — иначе скроем
  родственников. 27 номеров с несколькими учениками → в ревью.
- **Маск телефона `+7`**: не блокировать иностранцев — escape-hatch.
- **Семьи vs дедуп**: общий номер — это предложение «семья», а не слияние; слияния только
  по номер+имя с подтверждением и Undo.
