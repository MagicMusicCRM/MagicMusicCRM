# MagicMusicCRM — текущие продуктовые правила

Этот документ хранит только действующие продуктовые инварианты. Подробный статус
приёмки находится в owner UAT, а реализация — в текущем коде и миграциях.

## Авторизация и доставка кодов

- Для привилегированной роли email OTP обязателен, кроме явно указанного
  владельцем allowlist `AUTH_OTP_BYPASS_EMAILS`. Обход действует только после
  проверки пароля и фиксируется в audit.
- После правильного пароля OTP-сценарий открывается только если один из
  настроенных email-провайдеров фактически принял письмо. Если оба провайдера
  недоступны, сервер возвращает retryable `503 OTP_DELIVERY_UNAVAILABLE`, не
  выдаёт сессию и не оставляет пользователя в цикле ввода недоставленного кода.
- Фоновые OTP/reset-письма сохраняют retry-state и обе причины отказа
  (`primary + fallback`); исчерпанная доставка остаётся наблюдаемым фактом.

## Роли и scope

Иерархия: `client < teacher < admin < manager < director < system_admin`.

- Client видит только собственную область.
- Teacher видит назначенных учеников и своё расписание без staff-финансов.
- Admin работает с чатом, расписанием, клиентами и branch-scoped задачами.
- Manager получает операционный workspace назначенных филиалов без
  общешкольных финансов и финансовой аналитики.
- Director/system_admin управляют общешкольными финансами, конфигурацией и
  доступами.
- Финансы конкретной карточки клиента доступны Admin/Manager/Director через
  узкие client-finance capabilities.

Backend всегда проверяет capability и resource scope. UI не является security
boundary.

## Рабочие вкладки

- Каждая desktop-вкладка хранит собственную вложенную навигацию, фильтры,
  раскрытые панели и несохранённые значения формы. Обычное переключение вкладки
  не является выходом из формы и не вызывает Save/Discard; подтверждение нужно
  при закрытии вкладки или реальном уходе с её текущего экрана.

## Конфигурация CRM

- Lead и Student используют один typed custom-field storage и один набор
  определений для создания, редактирования, карточки и доски. Legacy
  `custom_data` остаётся только для исторической совместимости и не образует
  второй конструктор полей.
- Поддерживаются 16 типов, ширины `third/half/full` и независимые размещения
  `create/edit/card/table`. `card` без `edit` означает read-only.
- Архивирование определения или варианта скрывает его из активного выбора, но
  не удаляет сохранённое историческое значение.
- Значения системного поля источника настраиваются внутри этого поля, без
  второго справочника. Источник `Приложение` существует всегда и не
  архивируется; новый Lead/Student, созданный из зарегистрированного client-
  аккаунта, получает его по умолчанию. В карточке источник можно заменить на
  другой активный вариант, не переписывая историю старых значений.
- CRM-intake зарегистрированного Client выполняется при завершении онбординга;
  первое сообщение в чате только идемпотентно повторяет тот же сценарий. Уже
  связанный Student имеет приоритет над Lead. При единственном совпадении
  телефона существующая карточка связывается с app-аккаунтом без изменения её
  статуса, источника, филиала и истории; Student имеет приоритет над Lead. При
  нескольких совпадениях система не угадывает, не создаёт дубль и оставляет
  кандидатов директору для ручного выбора в управлении доступами. Новый Lead с
  источником `Приложение` создаётся только при полном отсутствии совпадений.
- Общешкольную конфигурацию меняют Director/system_admin. Manager может менять
  только разрешённый branch override; Admin/Teacher/Client не получают редактор.

## Чаты и сообщения

- Client общается со Staff через один чат `Администрация`; отдельный direct-чат
  с Client не создаётся. Между Teacher и Staff доступен обычный direct-чат.
- Text/image/file/voice — один message aggregate. Voice duration сохраняется на
  сервере. Активное media-сообщение обязано ссылаться на собственный private
  upload того же чата с соответствующими purpose и MIME; неуспешный message
  commit удаляет только что загруженный сиротский файл best-effort.
- Reply ссылается только на неудалённое сообщение текущего чата. Forward хранит
  source message ID и разрешён только из доступного actor чата. Private media
  другого чата повторно не привязывается; UI пересылает текстовую копию.
- Собственный текст можно изменить или удалить. Media удаляется в tombstone без
  физического удаления исторического message-факта. Реакции и read receipt
  сохраняются. В direct-чате закреплять может каждый активный участник;
  Administration и Group сохраняют свои привилегированные правила управления.

## Финансы

- Оплаты, сторно, возвраты, exclusions и technical history append-only.
- Статусы оплаты: `Не оплачен`, `Проведён, ожидает подтверждения`, `Оплачен`.
- Абонемент может покупаться со своего или чужого личного счёта, со скидкой,
  доплатой или рассрочкой; обязательство резервируется полностью.
- `payment_reminder_days` задаёт effective school/Branch-окно напоминания о
  предстоящем платеже рассрочки. Branch определяется по ученику абонемента, а
  уведомление `in_app + push` получают только активные Client app-аккаунты
  плательщика и его payer/parent-связей. Значение `0` означает напоминание при
  наступлении срока. На одну immutable installment создаётся одна durable
  reminder-запись; lease/retry использует стабильный notification ID и не
  дублирует карточку или push. Материализация `posted_pending` в дату платежа
  остаётся отдельным финансовым процессом.
- Отмена абонемента возвращает только допустимую сумму и не переписывает
  исходные факты.
- Типы списания и правила оплаты преподавателю конфигурируются; исторические
  snapshots неизменяемы.
- Записи истории ставок и выплат преподавателю создают операционные роли, но
  исправлять и удалять их из рабочего расчёта может только Director/system_admin.
  Удаление является audited void: строка остаётся для контроля, но больше не
  участвует в текущей проекции. Каждое исправление требует reason, expected
  version, idempotency и audit/outbox.
- Любая денежная команда сохраняет transaction, expected version,
  idempotency, audit/outbox и reconciliation semantics.

## Занятия и расписание

- Перенос, отмена и расчёт занятия используют один
  `reason → preview → commit` flow.
- Перенос запланированного индивидуального или группового Lesson через форму
  обязан реально изменить время, длительность или ресурс. Клиент либо Group и
  frozen participants не подменяются; reason, settlement и teacher pay
  подтверждаются единым signed preview с expected version и idempotent commit.
  После успеха вызывающий календарь или карточка дожидается повторного чтения.
- Постоянные планы именованные, индивидуальные или групповые, с conflict
  preview перед созданием и изменением, обязательными преподавателем и
  аудиторией, active/ended history и bounded tray. Невалидный preview не
  отправляет update и сохраняет все строки черновика для исправления; в
  групповом Plan конфликт привязан к конкретному ученику.
- Один индивидуальный Plan может объединять несколько дней с общими
  преподавателем и аудиторией и отдельные строки с другими преподавателями и
  аудиториями. Все строки создаются одной атомарной idempotent-командой и после
  commit перечитываются как части того же Plan.
- Один Schedule Analyzer обслуживает preview разовых Lesson и постоянных Plan.
  Он проверяет филиал, преподавателя, аудиторию, клиента/участников группы,
  группирует одинаковые конфликты по стабильному fingerprint и возвращает
  ranked-кандидаты: аудитория на то же время, ближайшее время, преподаватель с
  общей дисциплиной и комбинированная замена. Кандидат Plan проверяется для
  ближайшего конфликта и после применения обязательно проходит повторный
  preview всего периода; suggestion никогда не является разрешением обойти
  commit-validation.
- PostgreSQL хранит активные teacher/room/student/group bookings для каждого
  Lesson и защищает их `EXCLUDE`-ограничением по полуоткрытому интервалу.
  Frozen group participants входят в student bookings. Миграция выполняет
  preflight существующих пересечений и останавливается до установки constraint,
  если данные требуют явного reconciliation.
- Завершение Plan использует `reason → impact preview → confirmed idempotent
  commit`, общие series-locks с materializer и выбранную последнюю дату.
  Только будущие относительно этой даты незавершённые Lesson отменяются и их
  резервы освобождаются; terminal Lesson, tray и история сохраняются. После
  commit Plan неизменяем и перечитывается в ended-блоке. Причина и автор
  доступны управляющим CRM-ролям, но не Client.
- Tray постоянного Plan ограничен сервером и листается стабильным keyset cursor
  по `(scheduled_at, lesson.id)` в обе стороны. Ошибка перелистывания не
  сбрасывает уже показанную страницу, а retry повторяет тот же cursor и
  direction. Карточка показывает date/time, teacher, period и room;
  settlement/relation markers приходят из authoritative server projection.
  Завершённые планы по умолчанию свёрнуты.
- Schedule Plan — единственный пользовательский редактор постоянного
  расписания. Legacy `schedule-series` и старое поле `preferredSchedule`
  сохраняются только как совместимые исторические данные: карточка клиента их
  не показывает и не создаёт через них новые записи. Уже материализованные
  Lesson, завершённые планы и история не удаляются и не подменяются.
- В календаре карточки клиента «Скрывать чужие занятия» включено по умолчанию.
  Управляющая CRM-роль может локально раскрыть уже разрешённую ей branch matrix;
  target/other marker является отдельной проекцией и не меняет цвета
  `Забронировано`/`Завершено`/`Конфликт`. Контракт одинаков для Month, Week и
  обоих Day-режимов. Обычный Client не имеет доступа к staff schedule matrix и
  получает только собственные разрешённые lesson-проекции.
- Маршрут «Карточка клиента → Открыть в расписании» открывает месяц в основном
  филиале клиента с выключенным «Скрывать чужие занятия»: занятия целевого
  клиента выделяются зелёным, остальные остаются серыми. Кнопка «Создать
  занятие» наследует из этого маршрута клиента и его основной Branch; Room
  оператор выбирает вручную.
- Branch и Room обязательны при создании занятия. Для выбранного клиента Branch
  по умолчанию берётся из поля филиала его Lead/Student-карточки; Room остаётся
  ручным выбором Admin/Manager/Director.
- Преподаватель доступен для выбора только в активном назначенном ему Branch.
  Рабочие часы преподавателя и Branch являются блокерами, а Branch без
  настроенного графика не принимает занятия. Room должна принадлежать Branch;
  пересечения преподавателя, клиента и Room блокируются.
- Пользовательские уведомления о создании, переносе и отмене Lesson
  материализуются только из durable platform outbox с явным action и стабильным
  event ID. Client и новый Teacher открывают successor Lesson, снятый Teacher —
  исходный Lesson. Group audience берётся из frozen participant snapshot;
  удалённые и non-app identities исключаются. Retry не дублирует карточку или
  push, а технический state-only refresh уведомление не создаёт.
- При создании и переносе селекторы показывают только active преподавателей,
  назначенных в выбранный Branch, и active Room этого Branch. Занятость на
  конкретное время не дублируется локальной эвристикой: её авторитетно проверяет
  общий signed preview, который блокирует commit и показывает причину. При
  переносе финансовый каталог загружается для successor Branch.
- Discipline, категория и уровень обучения — информационные метаданные. Они не
  обязательны у преподавателя и не ограничивают создание занятий или филиалы.
- Lesson settlement и teacher pay создают immutable facts; исправление идёт
  через reversal/correction, а не update/delete истории.
- Director/system_admin может массово исправить ошибочную ставку и для уже
  рассчитанных занятий: старый teacher compensation fact не переписывается,
  создаётся superseding fact с обязательной причиной. Admin/Manager массово
  меняют только ещё не зафиксированные расчёты.
- Групповое занятие использует один общий settlement и optional явные
  per-client overrides. Состав для расчёта берётся из frozen snapshot с учётом
  append-only exclusions, а не из текущего состава Group. UI показывает имена
  участников и отправляет override только для изменённых строк; источник средств
  остаётся закреплённым за конкретным учеником/абонементом. На каждого активного
  участника создаётся ровно один client fact, на всё занятие — один teacher fact;
  reservation выбранного абонемента terminalize-команда переводит в `consumed`,
  а неиспользованные резервы этого занятия — в `released`, в той же транзакции.
- Перенос уже завершённого Lesson всегда отменяет его effective client/teacher
  эффект безопасной correction `free_lesson/none`, не удаляя старые facts и
  consumed reservation. Successor получает исходный frozen plan и отдельный
  reservation, после своего окончания проходит обычный exactly-once worker.
  Оператор указывает причину и новое время, но не выбирает фиктивные параметры
  reversal; UI обязан явно объяснить сохранение истории и повторный расчёт.
- При каждом создании Lesson обязательны тип списания, отдельное правило оплаты
  преподавателю и источник средств. UI может предложить допустимые значения по
  умолчанию, но оператор меняет каждый выбор отдельно. Для источника
  «абонемент» обязателен конкретный активный абонемент; неполный или
  несогласованный набор не создаёт занятие. При наличии активного абонемента он
  выбирается по умолчанию, личный счёт остаётся явной альтернативой. Источник
  «Без списания» допустим только когда и доля, и фиксированный штраф выбранного
  settlement равны нулю; платный или штрафной settlement требует абонемент либо
  личный счёт и fail-closed отклоняется до commit.
- «Пробное занятие» — независимый immutable marker, а не синоним бесплатного.
  Пробное занятие может быть платным или бесплатным; обычное занятие также может
  быть бесплатным. Деньги и часы определяет только settlement/source, а оплату
  преподавателю — отдельное teacher-pay rule.
- Scheduled Lesson не завершается до фактического окончания. Durable worker
  после наступления due-времени применяет именно заранее сохранённый frozen plan
  ровно один раз: client/teacher facts и terminal reservation фиксируются одной
  транзакцией; повторный polling не создаёт второй финансовый эффект.
- Если automatic completion исчерпал bounded retry, занятие становится
  `Конфликтом`, а staff видит безопасную причину и действие `Исправить расчёт`.
  Внутреннее сообщение ошибки не показывается и не выдаётся Client/Teacher.
  Исправление требует актуальную version и preview, завершается одной
  транзакцией и очищает состояние ошибки.
- Обычное `scheduled` занятие нельзя вручную отметить проведённым ни через UI,
  ни прямым settle API. Recovery settle разрешён только для
  `settlement_pending` с планом `review_required`.
- Пять правил оплаты преподавателю независимы от списания клиента:
  `none` даёт ноль, `standard` использует frozen ставку занятия, `percent`
  умножает стандартную сумму на процент, `fixed` задаёт сумму за занятие,
  `hourly` пропорционален frozen длительности. Ручное значение разрешено только
  для percent/fixed/hourly и при изменении catalog default требует причину.

## CRM и operations

- Lead/Student используют каноническую карточку со staff note, комментариями,
  задачами, коммерцией, расписанием и entity navigation.
- Staff/Teacher всегда создаются с единой технической identity/profile/link,
  но email и пароль необязательны. Если они указаны парой, доступ сразу рабочий;
  иначе `is_app_account=false`, а директор позже активирует ту же запись.
- Email и пароль меняются только dedicated access/profile-командами. Текущий
  login email и управляемый пароль Staff/Teacher доступны через отдельное
  чтение только Director/system_admin; каждое чтение пароля фиксируется в
  audit. Обычные Teacher/Staff payload не содержат email и парольные метаданные
  для остальных ролей. Для входа по-прежнему используется односторонний
  `scrypt`-хэш, а показываемая копия хранится отдельно в authenticated
  encryption. Пароль, установленный до появления этой копии, становится
  видимым только после следующей смены или переустановки. Self-service смена
  email/пароля обновляет ту же identity, поэтому директор видит актуальные
  значения. Обычное сохранение данных Staff/Teacher не требует доступа и не
  отправляет поля identity в профильный PATCH.
- Director/system_admin выбирает допустимую роль доступа уже при создании
  Staff/Teacher и может открыть её редактор прямо из карточки. Начальные роли
  сохраняются атомарно с identity; последующее изменение всегда выполняет ту же
  versioned access-команду, что и `Настройки → Доступ`, со сбросом персональных
  overrides, audit/outbox и проверкой иерархии. Director назначает только роли
  ниже собственной; `system_admin` не создаётся через обычную карточку.
- При создании и редактировании Staff/Teacher обязателен хотя бы один филиал,
  но можно назначить несколько филиалов одной операцией.
- Используется одна task-модель. Teacher не является получателем staff-задач.
  Admin видит branch-scoped задачи и по умолчанию `Мои задачи + Сегодня`.
  All-day и interval задачи показывают точное редактируемое время reminder;
  interval с окончанием не позже начала не сохраняется.
- Закрытие клиента завершает recurring work каноническими командами и сохраняет
  finance/history.
- Очередь проверки телефонов — рабочий сценарий, а не read-only
  список. CRM-writer либо исправляет телефон до канонического
  RU-формата, либо принимает его как есть; оба действия требуют
  причину. Исправление атомарно обновляет source entity и queue row
  под row lock; audit не хранит raw phone.
- Client может иметь только один активный запрос на удаление и может
  отменить его только в `pending`. Admin, Director и system_admin ведут
  `pending → processing → completed/rejected`; Manager видит запросы
  read-only. Terminal transition требует непустую причину.
- `completed` атомарно анонимизирует PII и login-данные точного
  target, удаляет identities/devices/tokens и отзывает sessions. Legal,
  consent, financial, lesson, operational и audit-факты не удаляются.

## Организационный lifecycle

Branch, Room, Group, Teacher и Staff нельзя считать завершёнными только потому,
что для них существует create/update.

- Branch закрывается через impact preview, blockers/remediation, reason,
  effective date и versioned commit. Commit атомарно переводит его из
  `active` в `archived`; историческая tombstone-запись, финансы, занятия, чаты,
  аудит и ревизии остаются. Будущая effective date отклоняется, пока нет
  scheduler и write guards для безопасного состояния `closing`.
- При создании Branch рабочие часы хотя бы для одного дня обязательны и
  сохраняются атомарно с карточкой филиала.
- Room архивируется только после проверки Group, future Lesson, recurring
  plan/series и будущих конфликтов. Preview обязателен; commit versioned и
  idempotent, история append-only. Restore разрешён только в активный Branch.
  Новые scheduling references на архивную Room блокируются на уровне БД.
- Group локально имеет versioned end/archive flow; планы, серии и будущие
  занятия сначала завершаются, roster и история сохраняются.
- Staff/Teacher локально имеют versioned offboarding: будущая работа сначала
  переназначается, затем одной командой согласуются CRM status, branch
  assignments, capability overrides, account и active sessions. Restore не
  возвращает отозванные персональные overrides.
- Discipline и Lead loss reason имеют versioned rename/archive/restore с
  обязательной причиной, preview, audit/outbox и append-only history.
  Архивное имя остаётся занятым той же UUID-identity; создать дубль вместо
  восстановления нельзя. Исторические lead transitions хранят snapshot имени
  и типа причины, поэтому переименование не переписывает старую аналитику.
- Branch discipline отвязывается только явной versioned-командой после preview.
  Активные Teacher/Student/Package показываются как impact, но не являются
  блокерами: справочник информационный. Восстановление возможно только при
  активных Branch и Discipline.
- Физическое удаление Discipline, Lead loss reason и Branch discipline
  запрещено. Новые активные ссылки на архивный справочник блокируются на уровне
  БД; merge дублей может изменить только `lead_id` исторической строки в узко
  разрешённой транзакции, не меняя её содержание.

## Аналитика и экспорт

- Период и Branch образуют один нормализованный фильтр для всех виджетов,
  drilldown и экспортов отчёта; смена фильтра не может оставлять секцию на
  прежнем scope.
- Manager не получает общешкольную финансовую аналитику: UI не показывает её и
  не запускает скрытый запрос, backend отдельно отклоняет доступ.
- Школьные расходы создаёт, изменяет и удаляет только Director/system_admin.
  Создание использует текущий Branch-фильтр, каждая mutation завершается
  API-readback. Действия доступны для всей загруженной истории, а не только для
  нескольких последних строк. Delete является soft-delete: строка исключается
  из текущих итогов/Analytics, но остаётся в БД с audit-событием.
- XLSX должен быть валидным OOXML, CSV — UTF-8 с BOM. Клиент проверяет формат до
  записи и честно сообщает, был ли файл открыт ОС или только сохранён по указанному
  пути. Экспорт должен совпадать с экраном по фильтру, колонкам, строкам и суммам.

## Состояния интерфейса

- Основной раздел обязан явно различать loading, empty, error и forbidden.
  Ошибка запроса не может выглядеть как пустой список или пустая область.
- Error-состояние не показывает raw exception и даёт действие, повторяющее тот
  же канонический запрос без потери текущего контекста. Ошибка проверки прав не
  равна подтверждённому forbidden.
