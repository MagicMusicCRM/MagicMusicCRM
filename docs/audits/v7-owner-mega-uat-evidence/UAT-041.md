# UAT-041 — поиск, полный набор фильтров и сортировка Lead

Статус: **PARTIAL**. Локальный UI/API/backend flow закрыт; актуальный
production owner-повтор ещё не выполнен.

## Закрытый разрыв

Backend уже умел фильтровать Lead по полям из импорта, но доска показывала
только филиал, статус, направление, уровень и категорию. Ответственный и
период отсутствовали даже в состоянии Flutter, а источник, тип обращения,
цель, пол и предпочтительное расписание существовали в модели, но не имели
доступного UI. Сортировка карточек не была пользовательской функцией.

Теперь desktop inline panel и mobile drawer используют один
`LeadBoardFilters` и дают одновременно выбрать:

- быстрый статусный срез, наличие задач и скрытие ставших учениками;
- филиал, статус, рекламный источник и ответственного;
- направление, уровень, категорию, тип обращения, цель обучения, пол и
  предпочтительное расписание;
- полуоткрытый период обращения `[from, to)` с явным сбросом;
- стабильную сортировку `Сначала новые` / `Сначала старые`.

Поиск остаётся в постоянном toolbar-поле, сохраняет focus и мгновенно
фильтрует уже загруженные карточки; применение любого вторичного фильтра не
стирает поисковый текст. Сброс очищает вторичные фильтры, сохраняя поиск.

## Канонический контракт

Карточка Lead и фильтр ответственного больше не имеют двух разных API-
клиентов: оба используют `MagicCrmService.listResponsibleStaff`, где ID —
`app.users.id`, совпадающий с `leads.assigned_to`. Источники читаются из
активного `GET /crm/lead-sources`.

`LeadBoardQuery.sort` допускает только `newest|oldest`. Backend применяет одно
направление одновременно к `row_number`, итоговой сортировке и keyset-
компаратору (`<` для новых, `>` для старых), поэтому догрузка не пропускает и
не дублирует карточки. Все фильтры входят и в выборку, и в per-column counts;
cursor исключается только из count query.
