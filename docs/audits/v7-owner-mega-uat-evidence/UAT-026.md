# UAT-026 — этапы и переходы Lead/Student

Статус: **PARTIAL**. Локальный UI/API/DB-кандидат закрыт; production owner
Release-повтор со второй сессией ещё не выполнен.

## Единый runtime

Lead и Student используют опубликованную school/Branch-конфигурацию этапов,
версий и `allowedTransitions`. Для Student доска получает effective
конфигурацию, разрешает drop только в допустимый этап и после сохранения
перечитывает серверные данные. Backend повторно проверяет тот же переход внутри
транзакции до изменения карточки и записи истории.

## UI-доказательство Student

Тест проходит production `StudentsBoardWidget` с этапами
`active -> paused`, `paused -> []`:

- перенос `active -> inactive` отклоняется самим `DragTarget`;
- перенос `active -> paused` отправляет PATCH существующего Student;
- после refetch счётчики меняются с `1/0` на `0/1`;
- сохранённая карточка отображается в новом столбце.

## API/DB-доказательство Student

PostgreSQL-сценарий публикует Branch revision с теми же разрешениями и через
реальный `CrmService.updateStudent` подтверждает:

- `active -> inactive` возвращает exact structured
  `422 {code: STUDENT_FUNNEL_TRANSITION_DENIED, field: status}`;
- `active -> paused` изменяет единственную карточку и агрегаты этапов
  `active: 1 -> 0`, `paused: 0 -> 1`;
- последующая попытка `paused -> inactive` отклоняется, агрегаты не меняются;
- в `student_status_history` появляется ровно один факт `paused`;
- rollback конфигурации создаёт новую immutable revision.

Lead configuration/history и общий draft/preview/publish/rollback flow остаются
на том же каноническом сервисе и покрыты соседними configuration tests.
