Статус: **PARTIAL**. Полный локальный UI/API/DB-кандидат пройден; production

## Создание карточки и доступ

Актуальная Director-форма создаёт Teacher с обязательными именем, филиалом и
ставкой. Дисциплины, категории и уровни являются необязательными справочными
метаданными и не блокируют создание карточки.

Email и пароль также необязательны, но должны быть указаны парой. Без них
атомарно создаются связанный технический user (`is_app_account=false`) и
Teacher; позднее Director может выдать доступ из карточки. С email/паролем та
же операция создаёт рабочий app account роли Teacher, сохраняет проверяемый
password hash и единственную `user_crm_links` связь.

Смена email/пароля самим пользователем и управление реквизитами Director
изменяют одну запись `app.users`. Teacher list/card читает email,
`password_configured`, `email_changed_at` и `password_changed_at` через эту же
связь, поэтому в карточке директора отображается актуальное состояние без
параллельной копии реквизитов.

## Филиалы и графики трёх преподавателей

Production `SystemSettingsWorkspace -> Расписание -> Графики преподавателей`
локально прошёл для трёх разных Teacher:

- каждый выбирается по ФИО в общем picker;
- филиальное назначение сохраняется отдельным versioned PUT;
- следующий PUT доступности использует обновлённую expected version;
- recurring rule понедельника сохраняется с timezone и временным интервалом;
- недоступность по датам нельзя добавить без видимой причины;
- Manager видит ту же область только для чтения, Director получает mutation
  actions.

Backend availability хранит assignments и rules единым каноническим runtime;
constraint engine повторно использует их как блокеры выбора преподавателя в
занятии.
