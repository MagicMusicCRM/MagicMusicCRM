# Группы: настройки расчётов, одиночные занятия и подбор преподавателя

Рабочая копия: `codex/ui-release-232`, HEAD
`8d259af13e918cdee2b6b7cec1f12c3eb1133798`, локальный кандидат на базе
`1.5.52+232`. Изменения не опубликованы в production.

Группа хранит ключи опубликованных типов списания и оплаты преподавателю.
Числовые поля цены и ставки убраны из создания и редактирования группы.
Новый план и одиночное занятие получают эти типы, филиал, преподавателя и
аудиторию из группы. Занятый преподаватель остаётся выбранным с предупреждением;
сохранение по-прежнему проверяет конфликт. В карточке доступно одиночное занятие
всей текущей группе. Источник средств и частичные минуты остаются решением по
участнику/занятию в рамках существующих прав.

Миграция `0162_group_lesson_defaults` добавляет две nullable-колонки и ограничение
парности. Старые группы нужно настроить явно; числовая история не используется
для угадывания типов. Существующие решения и финансовые факты не переписываются.
Одиночное занятие использует текущую версионированную команду, транзакцию,
idempotency, audit/outbox, снимок участников и резервы. Проверяются все участники;
конфликт откатывает команду целиком. Менеджер не может подменить оплату преподавателю.

Подбор доступных преподавателей в новом плане использует существующий endpoint
preview с пачкой кандидатов (не больше 100). Проверка каждого повторения читает
доступность ресурсов и конфликты один раз на ограниченный диапазон, затем
фильтрует отдельные интервалы. Кэш существует только внутри операции и одного
соединения; частичная привязка преподавателя возвращается к проверке каждого
интервала. Проверки записи и финансовые ограничения не ослаблены.

## Откат и граница выпуска

SQL down проверен внутри транзакции на изолированной БД с последующим rollback;
это подтверждает обратимость схемы до эксплуатации новых настроек, а не
production-откат приложения. После использования новых групп нельзя удалять
колонки с их настройками ради отката. План штатного отката: вернуть предыдущие
API и клиент, сохранив добавленные колонки и все созданные факты, затем проверить
версии, состав групп, резервы, денежные проводки, audit/outbox и reconciliation.
Совместимость предыдущего API с обновлённой реальной БД пока не подтверждена.

Для production нужны отдельная прямая команда владельца, свежий зашифрованный
backup, проверка его восстановления в изоляции, проверка предыдущего API на
восстановленной новой схеме и post-deploy reconciliation. До этой команды
production, каналы обновления и опубликованная версия остаются без изменений.
