Возвращать нужно только остаток, сохраняя F-05/F-06, текущие модели персонала, UI карточки и семантические цвета.

Для X-05/X-06 проверить два филиала и доступность во всех командах, поздний ответ после смены выбора, ошибки загрузки, ручную оплату/возврат к автоматике, отсутствие прав и конфликт без потери ввода. Принятие — UI → backend → сохранённое состояние → связанные экраны, с отрицательными случаями и очисткой fixture.

### RV-02 — полночь задач подтверждена только для списка

**Категория A/B, P2, REQ-012/013, X-08.** В [tasks_live_test.dart](../../../integration_test/tasks_live_test.dart), шаг `TASKS-X08-MIDNIGHT` (строки 499–545 исходного ревью), напрямую монтируется `SharedTasksPanel(now: () => clock)`. Часы двигаются с 20:59:50 до 21:00:01 UTC; проверяется исчезновение сегодняшней задачи и появление завтрашней. Навигационный badge в этом дереве отсутствует, часы backend не меняются.

В [shared_tasks_panel.dart](../../../lib/features/manager/presentation/tasks/shared_tasks_panel.dart) `_scheduleTodayRollover` обновляет дату панели; инвалидация `sectionUnseenProvider` явно есть после закрытия задачи. Возможность eventual refresh другими механизмами не исключена. **Дефект счётчика при полуночи этим ревью не доказан.**

Минимальный остаток: в изолированном контуре согласовать тестовый день UI и сервера; открыть настоящий staff shell, перейти через московскую полночь с известным набором задач, сверить список, badge и `/crm/sections/unseen`, повторить после reconnect/restart. Требуется сохранить один артефакт с тремя наблюдениями. До этого полная полуночная приёмка — NOT RUN, а не PASS.

Состояние fixture не позволяет объявить отсутствие конкретного урока дефектом данных. Однако этот PASS не доказывает критерий первого экрана. ### RV-04 — границы доказательств и сохранность артефактов

**Категория B, P2, завершающая приёмка.** Runner fingerprint в [http-journey-check.cjs](../../../scripts/http-journey-check.cjs) охватывает `integration_test`, `server/src`, приложение и scripts, но не обычный Flutter `test/`, `analysis_options.yaml`, `android/`, `windows/`. Формулировка handoff «включает tests» требует этого уточнения. Смена только Flutter-теста сама по себе не требует заново прогонять backend; требуется точная привязка того, что действительно изменилось и проверялось.

У installment-cycle после restart перезаписываются `partial-purchase-*.json`. Runner (строки 1897–1903) предварительно сохраняет только admin trace как `installment-cycle-admin.json`. [partial_purchase_live_test.dart](../../../integration_test/partial_purchase_live_test.dart) при restart завершает manager/director без исходных шагов. Текущие manager/director JSON поэтому пустые; логи и DB assertions по покупкам остаются. **Это потеря удобной пошаговой трассы, не доказательство выдуманного PASS.**

Для следующего финального прогона сохранять traces всех ролей до restart либо разные имена фаз; приложить manifest файлов, конфигурации платформы и тестов. Старые результаты не переписывать. Ещё один узкий дефект диагностического контура: `finance_access_live_test.dart` заканчивается `h.save()`, а не `h.finish()`; текущие сохранённые шаги PASS, но `completed=false`, и не следует считать внешний exit code достаточным без чтения шагов. Проверить завершение/провал harness перед использованием этого режима как gate.

Результат — полные X-05/X-06/R-04 с сохранением данных, запретами доступа, ошибками и конфликтами. Этот шаг можно начинать без нового бизнес-решения.
2. **Закончить остаток ST-06:** [промпт 06](prompts/06-today-tasks-and-results.md), только RV-02 и необходимая регрессия. Принятие — согласованные список, badge и серверный день в обычном shell, включая reconnect/restart. Переписывать работающий журнал задач не требуется.
3. **Дозакрыть ST-07:** [промпт 07](prompts/07-client-ux-and-lesson-visuals.md), RV-01/RV-03 и новое правило UI-01. Результат — полные X-07/X-09, реальные снимки нужных состояний и сохранение ошибок/прав. Локальный checkbox уже исправлен; не возвращать старую раскладку и пояснения.
4. **Повторить завершающий ST-08:** [промпт 08](prompts/08-integrated-candidate-acceptance.md). Сначала устранить потерю evidence RV-04, зафиксировать единый кандидат. Затем один X-10 на одной изолированной БД: лид → пробное → покупка → два занятия → наступивший взнос → задача → напоминание → закрытие → журнал. Дополнительно X-01…X-09/R-01…R-05 в применимых границах. Только после этих результатов решать готовность к merge и отдельному решению владельца о выпуске.

Каждый следующий агент начинает с актуального `git status`, инструкций и воспроизведения своего остатка; handoff не принимается на веру. Чужие изменения не откатывать. Не ослаблять права и проверки ради зелёного теста, не подменять внутренний backend mock-ответами в основных E2E, не объявлять незапущенную проверку пройденной. Новые зависимости, глобальный редизайн, новая финансовая модель и deploy этим ревью не назначены.
