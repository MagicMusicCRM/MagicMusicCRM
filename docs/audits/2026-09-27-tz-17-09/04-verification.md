## Условия и точные команды повторения

Проверки меняют только новые случайно названные БД собственного PostgreSQL. Для повторения нужен Docker, Node, Flutter Windows toolchain и установленный checkout. Порт 54339 должен быть свободен; контейнер с таким именем не должен уже принадлежать другой работе. Не использовать произвольный DATABASE_URL или стандартную production-конфигурацию приложения.

Из корня репозитория, PowerShell:

```powershell
docker run --detach --rm --name magiccrm-tz-audit-20260927 --publish 127.0.0.1:54339:5432 --env POSTGRES_USER=magiccrm_owner --env POSTGRES_PASSWORD=magiccrm_owner --env POSTGRES_DB=postgres --tmpfs /var/lib/postgresql/data postgres:17-alpine
docker exec magiccrm-tz-audit-20260927 pg_isready -U magiccrm_owner
docker exec magiccrm-tz-audit-20260927 psql -U magiccrm_owner -d postgres -c 'CREATE ROLE magiccrm_app NOLOGIN;'
$env:HTTP_JOURNEY_ADMIN_URL='postgresql://magiccrm_owner:magiccrm_owner@127.0.0.1:54339/postgres'
Remove-Item Env:HTTP_JOURNEY_IMAGE -ErrorAction SilentlyContinue
Remove-Item Env:HTTP_JOURNEY_ANDROID_SERIAL -ErrorAction SilentlyContinue
node scripts/http-journey-check.cjs --audit-customer-revisions
```

Это одноразовые тестовые credentials, не production-секреты. После завершения предыдущей команды остальные режимы запускаются **последовательно** с тем же HTTP_JOURNEY_ADMIN_URL:

```powershell
node scripts/http-journey-check.cjs --audit-partial-purchase
node scripts/http-journey-check.cjs --audit-teacher-availability
node scripts/http-journey-check.cjs --audit-tasks
```

V-03 из `server`, с тем же работающим контейнером:

```powershell
$env:TEST_POSTGRES_ADMIN_URL='postgresql://magiccrm_owner:magiccrm_owner@127.0.0.1:54339/postgres'
node test-tools/run-tests.cjs --runTestsByPath src/crm/tasks/shared-task-postgres.integration.spec.ts src/crm/schedule/constraint-engine-postgres.integration.spec.ts src/crm/commerce/subscription-issue-postgres.integration.spec.ts src/crm/clients/inbound-lead-postgres.integration.spec.ts
```

После завершения всех процессов runner проверить, что контейнер — именно созданный для этой проверки; `docker stop magiccrm-tz-audit-20260927` удаляет только его благодаря --rm. Базы каждого runner удаляются его finally; при аварии диагностировать только собственный cluster. Для чужих/production данных этот cleanup неприменим.

Фактический cleanup аудита: перед остановкой в pg_stat_database остались только postgres/template0/template1, активных runner-БД не было. Контейнер d4853d43503e (собственный postgres:17-alpine, loopback54339, tmpfs) остановлен и удалён. Чужой menu-bot остался запущен. Для повторения требуется заново выполнить подготовку выше.

Runner `scripts/http-journey-check.cjs:193` формирует ограниченное окружение backend, :205 выключает outbox/completion (кроме специальных режимов), :207 — installment/lesson reminder workers. SMTP/push/платёжные provider credentials не подключались. Harness выполняет API-login, использует memory stores и пустой CRM stream. Это реальные product widgets→HTTP→PostgreSQL, но не реальный login UI, OS restart, работа внешних доставок и не Release. Следующий агент обязан проверить флаги заново, особенно для X-01/X-03/X-04.

## Приёмочные UI E2E для следующих этапов

Это **будущие** сценарии X-ID. Общий статус каждого — NOT RUN в полном объёме, даже если отдельные шаги покрыты V-ID. X-02 на исходном HEAD — BLOCKED после неудачного CREATE. Точный новый test/runner flag добавляет соответствующий агент, если существующий режим не покрывает сценарий; не считать описание исполняемым тестом.

Общее: рабочий локальный Nest/PostgreSQL, синтетические уникальные fixture; основной путь через native Flutter UI, вторичное API/DB-чтение — только проверка сохранения. Использовать существующий integration_test/Windows или поддержанный Android-runner. Не навязывать browser automation Windows-клиенту. Для notifications нужен настоящий локальный worker/CRM socket и безопасный sandbox внешней доставки; для offline теста отключать только соединение своего клиента. Очистка каждого X — остановка своих клиентов/worker и удаление созданной runner БД, никогда ручное удаление production-истории.

## Достаточность и оставшиеся ограничения

Существующие integration тесты проверяют бизнес-факты/negative/concurrency, а не только структуру классов; их сохранять. Native suites доходят до реальных widgets и serverreads, но прямой запуск виджета+APIlogin обходят часть навигации. Слабые места доказательств: нечёткое paidUnits>0/<8 вместо точного 2, синтетические факты списания вместо 2UI уроков, отключённый CRM stream, trial время от часов запуска, высокий teacherviewport. Новые unit тесты в ходе аудита не создавались; будущие изменения проверять прежде всего E2E, не тавтологическими snapshot/implementation детекторами.

Ни production/Release Android, ни реальные SMTP/FCM/платёжные провайдеры не проверены. Нет свежего внешнего CI. Производительность и нагрузка не измерены; измеряемый budget задаётся от реального baseline при изменении конкретного пути, а не выдуманным SLA. Эти ограничения не мешают ST-01 и локальным slice этапам, но не позволяют объявить весь релиз готовым.
