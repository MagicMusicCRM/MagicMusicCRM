A — обязательно для ТЗ; B — необходимо для надёжности затронутого сценария. Дополнительные предложения категории C в обязательный план не включены. Приоритет P1 означает блокировку приёмки соответствующего сценария, а не доказанную потерю production-данных. Причины ниже подтверждены кодом, если прямо не помечены гипотезой. ## F-01 — Ручное создание лида вызывает desktop-уведомление

**A / P1. REQ-001–003 → ST-02 → X-01.** Подтверждение: статический FAIL, не аудиовизуальный E2E.

Ожидание: ручное создание/сохранение молчит, внешнее обращение уведомляет. Факт: `lib/main.dart:215` включает `leadNotificationListenerProvider`; `lib/core/services/lead_notification_listener.dart:26` принимает любой `lead/created`. Для admin/manager/director он показывает toast и, вне раздела клиентов, запускает звук. Ручной `LeadCommandService` эмитит именно это событие (`server/src/crm/lead-command.service.ts:115`). Источник создания listener не различает.

Воспроизведение для следующего этапа: два разрешённых Windows-сеанса, открыто расписание; вручную создать лид, затем отредактировать; отдельно создать внешний лид локальным inbound-контуром. Проверять системные уведомления/звук и сохранённое состояние, а не только внутренний API. В V-02…06 app-level listener и реальный CRM stream не испытывались.

Сохранить: realtime-инвалидацию списков, серверный scope, внешние лиды и напоминания задач, их idempotency. Минимальная доработка: разделить сигнал для пользовательского уведомления и универсальное событие изменения на существующем пути; сначала проверить существующие notification/outbox payload, не строить вторую систему уведомлений.

Риск: лишний шум маскирует реальные входящие. Немедленная и outbox-публикации могут давать повтор — **гипотеза**, проверяется подсчётом доставок одного события в двух сессиях. Не выдавать её за уже воспроизведённый дубль.

AMB-01 затрагивает отдельный listener `task/created`: буквальное «только» может запрещать уведомление о назначении. Это решение требуется лишь перед отключением этого канала, не блокирует исправление ручного лида.

## F-02 — График рассрочки не включает первый платёж

**A / P1. REQ-019–021 → ST-03 → X-04.** Статический FAIL.

Математика исправлена: `subscription_issue_pricing.dart:185` вычитает первый взнос из числа будущих. Но `subscription_issue_form_sections.dart:98` передаёт в график только `pricing.installments`, а `subscription_issue_components.dart:374` рисует только эти будущие строки с нумерацией с единицы. Первоначальный взнос остаётся отдельным полем, не строкой полного графика. Будущие даты в редакторе показаны без явного отличия прогноза от наступившего срока.

Воспроизведение: купить 4 урока за 14400, внести 7200, выбрать 2 платежа; до submit проверить график, после — обязательства и платёж. В текущем коде график имеет только будущую строку 7200. Конкретный UI-прогон этого примера не выполнялся; V-04 использует другую сумму.

Сохранить: точные minor units, `count−1`, preview/commit, отдельный ActualPayment, consumption duePolicy, существующий coverage. Первый платёж уже сохраняется в `subscription-purchase-persistence.service.ts:56`; нельзя создавать для отображения новый платёж/обязательство или переписывать исторические факты.

Доработка: согласовать отображение полного графика при покупке и повторном чтении, используя существующие факты и проекции; помечать прогноз до consumption. Приёмка: первоначальный 7200/оплачен + один будущий 7200/прогноз; итог 14400, повтор submit не удваивает суммы, третьего платежа нет.

## F-03 — Карточка не восстанавливает пропущенное CRM-изменение

**A+B / P1. REQ-008/018 → ST-04 → X-03.** Статический FAIL восстановления; обычный перенос с доставленным событием не объявлен сломанным.

`client_card.dart:803` явно игнорирует `event.isFallbackPoll`. `crm_realtime_provider.dart` выдаёт poll при недоступном socket. Реальный handler `client_card_realtime.dart` хорошо обрабатывает lesson/group, объединяет запросы, откладывает обновление при черновиках/неактивной вкладке. Однако очередь возникает только от полученного события; возвращение вкладки не восстанавливает событие, которого не было. Общая кнопка повторного чтения не найдена; retry autosave не заменяет reload всех связанных данных.

Сценарий доказательства: открыть карточку A, оборвать CRM socket, в B перенести урок, восстановить связь/активировать A; проверить UI и повторное серверное чтение. Отдельно оставить черновик заметки/контакта и убедиться, что восстановление его не уничтожает. В текущем harness CRM stream заменён пустым, поэтому V-02…06 не дают доказательств этого поведения.

Сохранить: batching, одну текущую загрузку, scope и защиту dirty-полей. Минимальная доработка — одна согласованная точка восстановления через существующий refresh, с доступным пользователю retry при ошибке; не запускать повторную загрузку каждого блока на любое событие. Риск: сотрудник сообщает клиенту старое время. Деградация производительности от нового refresh — риск для измерения числа запросов, не уже измеренный дефект.

## F-04 — Ученическая лента возвращает предшественников и отменённые уроки

**A / P1. REQ-009/016/035 → ST-04 → X-03.** Статический FAIL.

В lead-card фильтр правильный: `lead-card.service.ts:307` исключает successor и cancelled. Ученическая `student-lesson-timeline.repository.ts:132` вычисляет `actionable_lesson_id`, но выбирает исходные строки; условие на строке 291 исключает только archived и применяет время/scope. Перенос записывает successor/lifecycle, не архивирует предшественника. UI `student_lesson_timeline_controller.dart` убирает только одинаковые ID; `recurring_schedule_plan_view.dart` фильтрует тип списания, не всю цепочку. Подсказка перехода к successor не скрывает старый элемент.

Воспроизведение: ученик с одним уроком → перенос дважды на другие дни/страницы → снова открыть карточку → отменить текущий. Ожидается один актуальный урок до отмены и ноль после; исходные факты остаются доступны в истории. Текущий SQL допускает старые и cancelled-строки. Этот UI-сценарий в аудите не запускался, исходные DOCX-скриншоты не являются свежим подтверждением.

Сохранить: append-only переходы, финансовые связи, историю, scope, cursor-пагинацию и работу lead-card. Исправлять каноническую оперативную проекцию до вычисления страниц/count, а не скрывать уже загруженные строки на одном экране. Приёмка включает границы дат, страниц, повторное открытие, последнюю версию урока и разрешённое клиентское чтение.

## F-05 — Учительская неделя показывает недостоверную доступность

**A+B / P1. REQ-007/027 → ST-05 → X-05.** Статический FAIL двух состояний.

Ошибка загрузки reference в `schedule_widget_actions.dart:732` заканчивается пустым reference и выключенным loading, без явного error/retry. `schedule_widget_week_view.dart:116` трактует null как assigned, а пустые правила дают отсутствие заблокированных интервалов. Кроме того, строка 153 пропускает отрицательный интервал с null `endsAt`. Серверные `availability.rules.ts` и repository допускают бессрочную недоступность; constraint engine трактует её как продолжающуюся.

Воспроизведение: бессрочная занятость с текущей даты; отдельно отказ запроса reference при открытии недели. Сейчас код визуально допускает «пусто/свободно», хотя сервер может запретить запись. Реальный визуальный отказ/бессрочный интервал не воспроизводился. V-05 подтверждает конечные интервалы и их сохранение, не эти состояния.

Сохранить: канонические TeacherAvailability, timezone, branch assignment, поколения запросов при смене преподавателя. Доработка: отображать незагруженную доступность как неизвестную с повтором; обрезать открытый интервал границами видимой недели согласно контракту. Не подменять ошибку ответа пустой доступностью.

Приёмка: loading/error/retry различимы; бессрочный запрет виден; быстрое переключение преподавателей не показывает старые интервалы; запись и серверная проверка согласованы.

## F-06 — В выборе преподавателя нет проверки занятости до сохранения

**A / P1. REQ-017/028 → ST-05 → X-05.** Статический FAIL предложения; backend guard сохраняется.

`lesson_participant_section.dart:22` строит eligibleTeachers только по active и assignedBranchIds. Поле предлагает список с текстом «Занятость проверим перед сохранением» (строка 249). Это защищает сохранение через backend, но не выполняет P044: «в эти часы система не должна предлагать препода».

Воспроизведение: задать занятой интервал, открыть создание на пересекающее время — преподаватель остаётся доступным вариантом. Для edit учесть исключаемый собственный урок; для серии нельзя проверять только первую дату.

Минимальная доработка: применить существующий контракт доступности/constraint preview на подходящей общей границе редактора, показать недоступность и причину до submit. Гонка после выбора всё равно должна отклоняться сервером; неизвестная доступность не выдаётся за свободную. Сохранить все поздние guards и авторизацию.

Приёмка: свободный предлагается, занятый недоступен, изменение даты/длительности пересчитывает, сетевой сбой не теряет ввод, конкурентная запись даёт понятный отказ без частичного сохранения. V-03 проверяет overlaps/adjacency, но не полноту всех UI-команд.

## F-07 — Пробный E2E зависит от часа запуска; часть приёмки недостижима

**B / P1 для доказательства, не доказанный дефект продукта. REQ-005/010/011 → ST-01 → X-02.**

V-02: первая native-проверка проходит 6 шагов; второй тест открывает lead card, но CREATE ожидает один пробный и получает 0. Скриншот `lead-trial-admin-CREATE.png` показывает 22:00, 60 минут и корректное «Филиал закрыт в это время». Fixture закрывается 22:00. `integration_test/customer_revisions_live_test.dart:350` меняет дату на завтра, но не задаёт время; редактор наследует округлённое текущее время. EDIT/CANCEL не исполняются.

Причина подтверждена исходником, логом и свежим скриншотом, а не предположением о неработающей кнопке. Первый запуск V-01 отдельно остановился раньше на недостающей роли PostgreSQL; он не связан с данным дефектом тестовой предпосылки.

Следующий агент должен явно выбирать свободный рабочий слот fixture через настоящий UI и проверять предусловия; не ослаблять расписание/серверный guard, не менять ожидание 1 на 0 и не skip-ать тест. Удалять существующие проверки нельзя. Этот этап создаёт воспроизводимую базу, не объявляет весь пакет принятым.

Смежная граница: `live_audit_harness.dart` отключает CRM realtime. Новый отдельный сценарий восстановления должен включать настоящий локальный stream и workers по необходимости, сохраняя изоляцию внешних сервисов. Не менять глобально все тесты без причины.

## F-08 — Будущий остаток назван долгом до расхода оплаченных уроков

**A / P1. REQ-021/022/030 → ST-03 → X-04.** Свежий UI-факт + подтверждённая статическая причина.

V-04, `partial-purchase-admin-lead-REOPEN.png`: после покупки стоимость 7700, фактически оплачено 2000, остаток 5700 отображается красным «Долг:5700». В том же экране финансовая сводка показывает фактический долг 0. Покрытие ещё есть, срок будущего платежа не наступил.

`client_card_display.dart:238` `_subscriptionOverpayment` вычисляет paid−price и любой отрицательный остаток называет долгом. Он не использует фактическую просрочку/наступившее обязательство из commerce projection. Это расходится с D-02 и смыслом REQ-021. Минимальная доработка — различить остаток к оплате/прогноз/наступившее обязательство на существующих фактах; не создавать новый долг и не начислять деньги в wallet.

Надпись «Оплачено с учётом возвратов:0» в другом блоке берётся из счёта, а не оплаты абонемента (`client_card_student_tabs.dart:253`). Нулевой wallet корректен. Обобщающая подпись — **UX-риск**, а не доказательство пропажи платежа: уточнить область показателя так, чтобы 2000 в абонементе и 0 на свободном счёте не выглядели противоречием.

Приёмка: до расходования двух оплаченных уроков остаток не маркируется как наступивший долг; после consumption отображается одно реальное обязательство. Фактическая оплата и свободный счёт различимы без бухгалтерского знания; итоговые суммы/факты не изменены текстовой правкой.

## F-09 — Пустой список предлагает admin недоступное создание задачи

**B / P2. REQ-012/040 (сопутствующий UX) → ST-06 → X-08.** Свежий UI-факт V-06 и статическая причина.

После закрытия назначенной задачи admin видит «Создайте задачу, чтобы она появилась в этом списке», хотя создание ему запрещено и кнопки нет. Скриншот `tasks-admin-TASKS-ADMIN-CLOSE.png`; `lib/features/manager/presentation/tasks/shared_tasks_view.dart:234` задаёт подсказку без условия capability.

Это не основание выдавать admin право создавать задачи. Сохранить серверный запрет и корректное закрытие. Минимальная доработка — подобрать пустое состояние по существующим правам/фильтру: получателю объяснить отсутствие назначенных задач, создателю оставить доступный путь создания. Приёмка: обе роли понимают следующее доступное действие; у admin не возникает create-запроса. Данные и task-модель не меняются.

## UX/UI и эксплуатационные границы

| Сценарий | Проблема/риск | Требуемое поведение | Категория и приёмка |
|---|---|---|---|
| Ручной лид | шум и потеря значимости уведомлений | тишина для ручного, уведомление для внешнего | A, F-01/X-01 |
| Рассрочка | неполный график и ранний «долг» | первый взнос, прогноз, фактический срок различимы | A, F-02/F-08/X-04 |
| Перенос/другая вкладка | старые данные и лишние строки | текущая лента и восстановление без потери ввода | A+B, F-03/F-04/X-03 |
| Выбор времени/учителя | неизвестное выглядит свободным | состояние загрузки/ошибки, недоступные предложения | A+B, F-05/F-06/X-05 |
| Карточки/настройки/задачи | клавиатура, фокус, маленькая высота и все error-states не проверены | завершение сценария при штатном viewport и ошибках | проверка A/B, X-07/X-08; дефект объявлять только после воспроизведения |

Backend integration V-03 доказывает отдельные транзакции/rollback, scope, idempotency, concurrency и business-predicates, не целую production-систему. Миграции применялись только к новым временным БД; совместимость с реальной историей требует отдельной обезличенной fixture/backup для release. Производительность не измерялась: количество native-запросов есть в JSON, но p95/нагрузочный вывод не сделан. Проверку ограничить изменяемыми сценариями и измерять задержку до/после на одинаковых данных; новая очередь/кеш без измеренного основания не нужны.

Ни один пункт категории C не является обязательной реализацией. Новые аналитические панели, pixel-copy Hollihop и общий редизайн приложения исключены.
