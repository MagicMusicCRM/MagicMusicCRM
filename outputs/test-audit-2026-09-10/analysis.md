## 1. Приоритет высокий: обычная команда не воспроизводит полный серверный gate

[package.json](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/server/package.json>) запускает Jest последовательно; [jest.config.js](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/server/jest.config.js>) использует стандартное окружение `node`. Создания чистой БД на suite в этой команде нет.

Работающий механизм найден в [run-isolated-tests.cjs](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/dist/release218/run-isolated-tests.cjs>) и [isolated-test-environment.cjs](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/dist/release218/isolated-test-environment.cjs>): новая БД-шаблон, миграции и backfill, затем отдельный клон на каждый suite. Оба файла игнорируются Git. Новый checkout не получает эту часть проверенного процесса.

Одновременно 11 серверных файлов, содержащих в release evidence 42 случая, выбирают `describe.skip`, если не задан адрес БД. Среди них HTTP-контракты оплат и расходов, переводы счёта, refresh token reuse, проверки миграций и блокировок. Свежая выборка подтвердила: 8 таких проверок можно пропустить с успешным exit code. Это **не означает**, что весь `npm test` без БД пройдёт: другие suites используют localhost fallback и могут упасть.

Например, [subscription-lesson-race-postgres.integration.spec.ts](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/server/src/crm/commerce/subscription-lesson-race-postgres.integration.spec.ts:12>) использует общую локальную `magiccrm` по умолчанию. [student-account-transfer-postgres.integration.spec.ts](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/server/src/crm/finance/student-account-transfer-postgres.integration.spec.ts:11>) требует явного адреса и создаёт fixtures, которые изолирует внешний runner. Последовательное выполнение не заменяет изоляцию состояния.

**Что исправлять:** перенести существующий механизм в отслеживаемые test tools и дать ему штатную команду. Разделить быстрый набор и полный DB gate; в полном gate обязательные DB suites должны завершаться ошибкой при отсутствии окружения или при unexpected skips. Не создавать второй механизм БД.

## 2. Число PASS сильно зависит от одной матрицы

[subscription-preview-token.spec.ts](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/server/src/crm/commerce/subscription-preview-token.spec.ts:692>) даёт **1289 из 4115 серверных случаев — 31,3%**. Внутри есть 955 invalid-payload сценариев и 136 случаев own-present undefined, проверки подписи, доменов, срока действия, структуры и порядка чтения свойств.

Матрица полезна для границ подписанного протокола и в выпуске заняла около 1,5 секунды. Большой объём сам по себе не причина её сокращать. Но 1289 PASS здесь нельзя трактовать как 1289 различных пользовательских сценариев оплаты.

Есть проверки, фиксирующие детали реализации: точный Proxy access trace, порядок short-circuit, точные размеры корпуса. Их стоит отделить от обязательных внешних контрактов и проверить необходимость при следующем изменении кодека. Совместимость токенов нельзя менять только ради упрощения тестов.

Побайтных дублей среди 601 тестового файла не найдено. В серверном результате есть 9 повторов полного имени теста, преимущественно у параметризаций. Это повод улучшить подписи параметров, **не доказательство дублирующего поведения**. Семантическое дублирование всех assertions ещё не установлено.

**Что учитывать в отчётах:** отдельно число бизнес-инвариантов, сценариев, вариантов данных и уровней исполнения; количество PASS сохранять как техническую статистику.

## 3. Название файла не определяет границы проверки

В 14 из 26 device-файлов найдены маркеры подмен API/services. По исходнику подтверждено, например, что [role_personas_device_test.dart](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/integration_test/role_personas_device_test.dart:374>) подменяет API и capability snapshot, а [lesson_settlement_device_test.dart](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/integration_test/lesson_settlement_device_test.dart:30>) реализует собственный API fake.

Они полезны для UI, layout, обработки состояний и отсутствия запрещённых клиентских запросов. Они не доказывают серверный RBAC, настоящую транзакцию и совместимость с текущей схемой БД. Для остальных device-файлов отсутствие поискового маркера само по себе не доказывает реальный HTTP.

В 11 серверных тестовых файлах используется PGlite. В [finance-balance-postgres.integration.spec.ts](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/server/src/crm/finance-balance-postgres.integration.spec.ts:46>) таблицы и views создаются вручную. Это реальное выполнение SQL в встроенном движке, однако такой тест не подтверждает весь набор production constraints, миграций, соединений и межтранзакционных блокировок. Тесты отдельных исторических миграций на старой схеме могут быть намеренными и необходимыми.

Есть и сильный сквозной уровень: [employee_journey_live_test.dart](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/integration_test/employee_journey_live_test.dart:29>) работает с настоящими формами, HTTP и PostgreSQL. Он проверяет потерю ответа после commit, retry, конфликт редакторов и сохранение финансовых результатов. Его границы честно описаны в [RELEASE-JOURNEYS.md](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/docs/engineering/RELEASE-JOURNEYS.md>): test launcher, логин через API, отключённый push; это не весь маршрут установленного приложения и не все роли.

**Что исправлять:** обозначить типы исполнения в runner/инвентаре: pure unit, UI с fake, embedded SQL, migrated PostgreSQL, real HTTP, device journey. Проверить для ключевых правил наличие связки уровней, а не требовать реальную БД от каждого unit-теста.

## 4. Подтверждён дефект статической проверки доступности

[accessibility_inventory_test.dart](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/test/features/workspace/accessibility_inventory_test.dart:9>) ищет строку `IconButton(`, затем ищет `tooltip:` до следующей такой строки или до конца файла. Граница вызова конструктора не учитывается.

Если после кнопки без подписи находится `IconButton.filled(tooltip: 'Другая кнопка', ...)`, первая кнопка ошибочно считается подписанной. Именованные конструкторы `IconButton.filled(...)` вообще не попадают в этот поиск. Аналогичную схему границ использует проверка FAB.

Свежий тест проходит, а отдельный воспроизводимый пример показывает обе слепые зоны. Проверка semantics в этом же файле монтирует искусственную кнопку, поэтому не закрывает дефект сканирования production widgets.

**Что исправлять:** анализировать конкретные вызовы через уже имеющийся Dart AST-инструментарий и проверять semantics важных реальных UI-поверхностей. Добавить минимальные отрицательные примеры для самого guard. Не заменять все архитектурные тесты: в проекте уже есть более точные AST/dataflow guards.

Маркеры чтения файлов встречаются в 34 клиентских и 57 серверных файлах. Это список для сортировки, не число «плохих текстовых тестов»: туда входят чтение fixture, SQL миграций и валидные архитектурные проверки.

[visual_baseline_test.dart](</C:/Users/Alinka/Documents/Codex Import/MagicMusicCRM/test/features/workspace/visual_baseline_test.dart>) проверяет шрифты, токены, reduced motion и размещение error state при увеличенном тексте. Это полезные проверки, но сравнения изображения с эталоном здесь нет. Поиск `matchesGoldenFile`, `goldenFileComparator`, `screenMatchesGolden` в test/integration_test совпадений не дал. Сохранение screenshots для осмотра и автоматическая визуальная регрессия — разные виды доказательств.

**Что делать:** снять новое покрытие для явно определённых наборов и сопоставить критичные ветви с assertions. Для выбранных стабильных экранов отдельно определить визуальные проверки. Отсутствие общего процента не равно отсутствию тестов.

## Что уже стоит сохранить как основу

| Правило | Подтверждённая проверка в текущих тестах | Граница доказательства |
| --- | --- | --- |
| Повтор команды оплаты не создаёт второй финансовый эффект | payment HTTP/PostgreSQL, shared wire fixtures, Flutter retry, employee journey | Разные уровни связаны общими форматами; настоящий прогон DB нужен отдельно |
| Не хватает оплаты — нет списания и начисления преподавателю | completion worker: settlement_pending, нулевые факты, audit/outbox; два завершения на одном счёте | PostgreSQL-тесты проверяют результат и конкуренцию |
| Замена абонемента сохраняет израсходованную стоимость и долг | full-volume replacement policy + replacement PostgreSQL suites | Исторический учёт нельзя удалять как legacy |
| Серверная роль и scope остаются авторитетными | actor matrix, HTTP payment revoked-role checks, student membership parity | UI role fakes дополняют эти тесты, но не заменяют их |
| История изменения расчёта сохраняется | completion worker/correction assertions сравнивают исходные и новые факты | Проверяется сохранённое состояние, а не только ответ метода |

Это выборочно проверенные положительные примеры. Полная матрица всех действующих продуктовых правил и отрицательных сценариев ещё не составлена. Упоминания v4/v7, старых DTO или исторических схем сами по себе не делают тест устаревшим: проект сохраняет историю и совместимость.

## Порядок дальнейшего пересмотра

1. Сделать штатным существующий изолированный серверный runner и контроль обязательных skips. Критерий: новый checkout запускает тот же полный набор без скриптов из release artifacts.
2. Использовать инвентарь как основу классификации; отдельно маркировать fake/API/DB/историческую совместимость. Критерий: каждый тип PASS имеет понятную границу доказательства.
3. Сопоставить деньги, абонементы и завершение занятий с текущими правилами: вход, отказ, повтор, конфликт, audit/outbox, сохранённые факты. Критерий: у каждого правила есть конкретный тест или явно записанный пробел.
4. Исправить доказанные ложные PASS в guards; дубли сокращать только после сравнения входов, assertions и обнаруживаемых дефектов. Критерий: намеренно сломанное правило действительно делает проверку красной.
5. Обновить coverage и разделить быстрые проверки, PostgreSQL и device/release gate. По сохранённому прогону стоит исследовать стоимость schedule-plan suite (~136 с) и audit-presentation coverage (~83 с); эти времена зависят от окружения и не являются новым benchmark.
