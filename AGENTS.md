# AGENTS.md — MagicMusicCRM

Этот репозиторий использует RepoWise как основной инструмент навигации по коду,
поиска зависимостей и оценки риска. Правила ниже намеренно короткие: они защищают
данные и архитектурные инварианты, но не навязывают отдельный процесс ради
процесса.

## Начало работы

1. Прочитать этот файл и проверить `git status --short --branch`. Чужие
   незакоммиченные изменения не откатывать и не включать в свой коммит.
2. Для незнакомой области один раз запросить RepoWise overview, затем переходить
   к точечным `get_answer`, `search_codebase`, `get_context` и `get_symbol`.
3. Перед широким или рискованным изменением использовать `get_risk`. Для
   рефакторинга дополнительно использовать `get_health`, для cleanup —
   `get_dead_code`, перед merge — `get_change_risk`.
4. Если RepoWise сообщает `low confidence`, `mock` или
   `semantic_search=false`, проверить вывод по живому исходнику через `rg` и
   чтение конкретного файла. Индекс помогает найти код, но не заменяет код.
5. Текущий production/UAT-контекст читать в
   `docs/architecture/NEXT-AGENT-HANDOFF.md` только когда задача его затрагивает.

Для мелкой локальной правки не нужно создавать отдельную спецификацию, task ID,
отчёт или архитектурную фазу. Документ обновляется только если реально меняется
продуктовое правило, архитектурное решение, runbook или проверяемый статус.

## Источники истины

При конфликте приоритет такой:

1. Последнее прямое решение владельца.
2. Наблюдаемое поведение актуальной Release-сборки и production API/DB.
3. Текущий production-reachable код, миграции и тесты.
4. `docs/product/CURRENT-PRODUCT-RULES.md` и
   `docs/architecture/CURRENT-DECISIONS.md`.
5. Аудиты и release evidence — только для зафиксированного в них кандидата.

Старый PASS не подтверждает новый кандидат. Наличие endpoint, widget или теста
не доказывает доступность пользовательского сценария через UI.

## Неподвижные инженерные правила

- Один Flutter/NestJS/PostgreSQL runtime. Не создавать параллельные модели
  оплат, задач, расписания, навигации или event store.
- Flutter UI работает через существующие services/providers; прямой доступ к
  БД или Supabase из widget запрещён. Riverpod — основной shared state.
- RBAC и resource scope проверяет backend. Скрытый или запрещённый UI не должен
  запускать запрос.
- Денежные и lesson-команды сохраняют transaction, expected version,
  idempotency, audit/outbox и append-only факты. Историю нельзя удалять для
  сокрытия дефекта.
- Организационные сущности с историческими связями закрываются через
  preview/blockers/commit и архивирование, а не физическое каскадное удаление.
- UI-текст — русский; код и комментарии — английские.
- Единственная тема — Deep Charcoal & Sophisticated Gold. Светлая тема, glow,
  яркие градиенты и legacy-стили не возвращаются.
- Секреты, env, PII, production dumps, backups и Office lock-файлы не
  коммитятся.

## Проверка и production

- Исправлять корневую причину в общей точке и запускать минимальный релевантный
  тест. Полный Flutter/backend/release gate нужен для release-кандидата, а не
  для каждой правки документации.
- После структурных изменений обновить локальный индекс:
  `repowise update --index-only`.
- Изменение production или deploy разрешены только по прямой команде владельца,
  с новым backup, проверяемым rollback plan и post-deploy reconciliation.
- Не выполнять ручное удаление production-данных и не переписывать финансовую,
  учебную или audit-историю.

Краткий RepoWise-процесс: `docs/engineering/REPOWISE-WORKFLOW.md`.
